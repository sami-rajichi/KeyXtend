# Security note: kx-platform-windows

- **Owner:** product owner
- **Last review:** 2026-10-31 (P8 security check: the worker's restricted token and the file check that probes only drive paths; P8 task 16: the clipboard services' gates and the history's drive; P8 task 9: the media worker's start and its review fixes; P7 security review: what the focus handler reads, a provider's long text, forged sealed blobs and the pack index cap; P7 DoD review: the selection and the check's kind; B12 review: `TextPattern2`'s caret first, a failed `GetSelection` unsure)
- **Status:** Reviewed
- **Scope:** `crates/kx-platform-windows`, inside the uiAccess `keyxtend` process:
  - basics: the QPC clock, the program and per-user folders, COM start-up, the uiAccess check and where libraries load from (`dll`);
  - input: injection (`inject`, `strokes`, `keys`), shortcuts (`shortcut`), the power dialog (`power`) and the mouse and keyboard hooks that host the hold engine (`hook`);
  - layouts: reading them and the switch request (`layouts`, `langinfo`), and the app in front (`front`);
  - windows: the window guard, its entry watch and window queries (`window`), the scroll target (`scroll`), screens (`screen`), DWM backdrops (`backdrop`) and the graphics adapter the UI draws on (`gpu`);
  - system: the look and its watcher (`sysui`, `watch`), the one running copy with its command window (`instance`, `hidden`), the tray icon with its window and front-window hook (`tray`), the heaps' free pages after a look change (`memory`) and the speaker on `XAudio2` (`sound`);
  - P7: the UI Automation client the scroll target, the box watch and the gates share (`uia`), the focused-box watch (`field`), the data key's DPAPI guard (`guard_key`) and the word-pack file maps (`packs`);
  - P8: the clipboard watch, writer and file facts (`clip`, moved from the gate tool's spike code), the local calendar (`calendar`) and the folder reveal through the running Explorer (`reveal`).
  - P8, the media worker's start (`worker`): its token, pipes, inherited handles and job; the neutral host in `kx_platform::pictures` drives it (`kx-platform.md`).
  - P8, the clipboard history's drive (`disk`): the free bytes and the volume root of the folder the app gives its sealed shelf.

## Capabilities
| Capability | Why needed | What breaks without it |
|---|---|---|
| None held | The adapter implements ports; the kernel grants capabilities to the modules that use them. The injector's, layout source's and shortcuts' service keys need `InjectInput`, the power dialog's needs `Power`, the box watch's needs `ReadFocusedText`, the clipboard watch's (`ClipboardKey`) needs `ReadClipboard`, the clipboard writer's (`ClipboardWriterKey`) needs `WriteClipboard`, and the packs', pictures' and calendar's need none. The key guard is no service: `kx-crypto`'s sealed files use it behind `SealedStoreKey` and its sealed shelf behind `SealedShelfKey`, both needing `SecretStore`. `WinDiskRoom` is no service either: only that shelf reads it. `WinReveal` is a UI port the app hands the ui, with no gate. | N/A |

## Threats (STRIDE-lite)
- **Spoofing:** a shell or parent process could set `LOCALAPPDATA` or `TEMP` to aim our data elsewhere. Mitigation: the folder comes from the known-folder API, not the environment.
- **Tampering:** our own injected input could loop back through our own hooks (P4) and be acted on twice. Mitigation: every event carries `keys::TAG` (the keyboard) or `keys::REPLAY` (the hold engine, with each act's id in its low 16 bits) in `dwExtraInfo`, and our hooks never act on either, except our keyboard's `TAG` Esc, which only cancels a carry; the tags are pinned by a test.
- **Logging / repudiation:** `PlatformError` never holds a path, `InjectError` holds only counts and `UiError` at most an OS error code. The injector, the layout source and the shortcut, power, window, look, tray and memory parts log nothing; `Kept` and `Read` hide their points and boxes in debug output.
  - `ShortcutError` and `PowerError` hold only counts or a fixed kind. The shortcut tables' `TableError::Parse` holds TOML's message about our own compiled-in tables and is never logged, as a table that does not parse leaves the list empty. The field table's `TableError` is logged, as it too names only our compiled-in table.
  - The scroll part logs only a fixed warning, with the start error at most, when a run's UI Automation (its thread, COM or client) or ping thread does not start; never a point, a box, a percent or a title.
  - The pointer hook logs only counts, never a point or a key (a panic in its callback: see Accepted), and the speaker logs only a warning kind, an HRESULT or a wait in ms, never a clip.
  - The box watch logs only fixed warnings, with an error or HRESULT at most, for a thread, COM, client, handler or table that fails and for each caught callback panic; never text or a count of text. The key guard and the packs never log, and no pack error names a path.
  - The debug output of key events, decoded keys, the hook's records (`Held`, `Queue`) and a batch's `Input` never shows a key, a unit or a point (`the_records_and_a_batch_hide_every_point_and_key_in_debug`).
  - Layout names and characters are not typed text, but a caller must never log `Scan` values next to what the user typed.
- **Information disclosure:** no network; nothing leaves the process. Text is read only through `Redacted::expose` to build the send.
  - A copy a password manager marks (`ExcludeClipboardContentFromMonitorProcessing`, `Clipboard Viewer Ignore`, `CanIncludeInClipboardHistory` = 0) is reported `Marked` before a byte or size of it is read, and a table that does not parse refuses the watch. Our own writes set the marker before any part and turn Windows' cloud clipboard off, so an Insert never adds a row here or in Windows' history.
  - The clipboard part logs only one fixed warning, when its compiled-in table does not parse; never a part, a path, an app or a size.
  - The entry watch keeps a point only while the scroll module runs, as the keyboard asks for it only then (`kx-ui.md`); `unwatch_entries` at the module's stop and the keyboard window's end forget it (`window/entry.rs` `unwatch_entries`, `forget`).
- **Denial of service:** start-up fails with a typed error, never a panic, when Windows refuses the clock or a folder.
  - A huge copy is handed on to nobody (`TooBig`), and the formats after the one that passes the cap are never fetched; another app holding the clipboard costs the watch or a write `open_ms` at most, then `Busy`. A copy that renders late can still hold the watch thread (see Accepted), and dropping the watch waits its `STOP_WAIT` at most.
  - After a partial send it tries to release every key still held, and once more one event at a time for what Windows refuses, so no modifier should stay stuck down. A mask key (`keys::MASK_VK`, unassigned) goes first when Alt or Win is released, so neither opens the menu bar or Start.
  - The speaker's queue is bounded (`QUEUE`): a play past it is dropped, so `play` never waits. Dropping the speaker waits at most its `STOP_WAIT` for its thread, then warns and leaves it.
- **Elevation (layouts):** `request` posts only `WM_INPUTLANGCHANGEREQUEST`, with a layout checked against the installed list, to the window that has the keyboard, which decides whether to switch; with uiAccess the post may reach a window above our integrity level, which is why the port needs `InjectInput`. The adapter never loads, activates, adds or removes a layout; only the test window's `--layout` activates one (see Accepted).
- **Tampering (layouts):** the layout names come from `HKLM`, which only administrators can change; they are display text, bounded and never run or parsed further.
- **Tampering (guard):** the guard puts its procedure in front of visible windows of our own process only, on the thread that owns them (Windows refuses any other). It keeps no global state beyond a per-thread list of the windows it is lifting back, a per-thread recheck flag and its message id, and unhooks itself on `WM_NCDESTROY`, so no procedure outlives its window.
  - A tip's lift (`lift_alone`) moves only visible windows of our process with that title, never activates them and leaves their owners in place, and a guard run's `top` title only changes the order in which it guards those same windows.
  - `lay_under` moves only our shown windows with that title (the scroll outline's edges), just under our own window titled `under`, never activating them; `watch_entries` marks only a window the guard holds, and `mark_pages` only our own shown window, which it guards first, so each mark goes with its window. `unwatch_entries` only removes the watch's marks from our own windows and forgets the kept point.
- **Tampering (topmost):** another program's `SetWindowPos` that drops a guarded window out of the topmost band (`HWND_NOTOPMOST`, `HWND_BOTTOM`, or after a plain window) is undone at once: the guard lifts it back, with the windows it owns, without activating it.
  - Windows drops an owner with its owned window and may tell only that window, so the guard lifts the furthest guarded owner too (a shadow with its keyboard), then every guarded window that owner owns, each above its owner. It follows only owners it guards on the same thread, so another program cannot draw a window of its own into the lift.
  - A lift made inside another program's call may not land, so the guard posts itself a recheck that runs after the window has answered the move; that program may still be busy then, and a recheck that runs too early is not repeated. A recheck posts none, so the checks always end, and another program that posts it only triggers the same check.
  - The guard calls `SetWindowPos` only on windows of its own thread, though Windows still moves their owner and owned windows with them. Settings is not guarded, so it can still go behind other windows.
- **Tampering (scroll):** a turn goes only to the window under the pointer or at the kept point, or to the first other app's window behind ours when our window now covers that point, never to ours: a posted `WM_MOUSEWHEEL` or `WM_MOUSEHWHEEL` that carries numbers only, a `SendInput` wheel tagged `TAG` only while the pointer is still on that window and Windows routes wheels to the pointer, or UI Automation's line steps, which start at the target point only while the target is the window there, else at that point inside the target's own window. While our open list shows, the aim is ours and nothing turns. With uiAccess a post may reach a window above our integrity level, which is why the port needs `Scroll`.
  - Without uiAccess, UIPI refuses those posts, so the turns come back `Refused` and their lines drop, and a ping UIPI blocks (`ERROR_ACCESS_DENIED`) counts as answered, so the window is never held back as busy.
  - What UI Automation reads from another app, even an elevated one, is typed values only, a box and two percents, never text to parse (ADR-0004); `area` and `along` refuse a bad box or percent, NaN included.
- **Denial of service (scroll):** the run never waits on the target: posts return at once, pings and UI Automation run on threads of their own, and a window that left a ping unanswered or that Windows calls hung gets nothing, so no turns pile up behind a busy app. A stuck UI Automation call costs a read `read_ms` at most, with nothing piled up behind it.
- **Denial of service (click-through):** only a window that let clicks through when first guarded (tips, shadows) keeps click-through; on any other, the guard refuses `WS_EX_TRANSPARENT`, so no program can make the keyboard click-through.
- **Spoofing (command window):** the command window is message-only and reachable from this session only: Windows keeps window messages inside one desktop, and UIPI drops posts from a lower integrity level. A post does not name its sender, so the window acts only on a code from the fixed table (`show`, `quit`); a program that can post there runs as this user at our level and could end the process anyway.
- **Denial of service (UI parts):** a panic in a look or command callback is caught before it reaches Windows, and the next change or command is still heard. Another program's `WM_CLOSE`, or a `WM_QUIT` it posts to the window or to its thread, cannot end the command or watch window: the loop ends only on `stop`'s `WM_QUIT`, sent after `stop` sets its flag.
  - Dropping a claim or a watch waits for its thread, and so for a running callback, unless its quit message could not be posted; a callback must never wait for the thread that drops it. A flood of look broadcasts costs one reading each and calls back only on a real change; a failed OS read gives a safe default, never a panic.
- **Spoofing (tray):** the tray window takes the taskbar's callback and `TaskbarCreated` from any program in the session, which UIPI would otherwise drop from below our level; a forged message can only open our own menu or add our icon again. The front-window hook reads class names only, never titles or content, and skips our own windows.
- **Denial of service (tray):**
  - A panic in the tray listener is caught before it reaches Windows.
  - Adds and changes run from the icon's own queue and no lock is held during a taskbar call, so a message that arrives inside the call cannot deadlock the thread, and neither `show` nor `set` waits on the taskbar: a hung Explorer stalls only the icon's thread, never the keyboard. A change queued behind an add, or behind a taskbar restart, follows the add.
  - The icon's thread deletes the icon as its window ends, after any add it had queued, so no dead icon stays behind while the app runs.
  - The front-window hook, the only hook in P3, runs out of context with our process skipped; it reads one class name and queues a wake inside `catch_unwind`, so it cannot stall anyone's input.
- **Spoofing (pointer hook):** another program can put our tags on its input.
  - `TAG` or `REPLAY` hides that input from the engine. A forged `REPLAY` event that names an act of our newest batch ends the wait for our echo early, so the hand's next event may overtake our input; a forged `TAG` event does not.
  - Such a forged echo can also make the record of held input forget a press of ours that is still in flight (see Accepted).
  - A forged `TAG` Esc can only cancel a carry, as the engine hears our keyboard's Esc in the physical mode.
  - `SIM_TAG` acts only in the simulated mode, which exists only in builds with the `sim-input` feature (the gate tool's, never the shipped app). In the physical mode no other injected input acts.
  - The health check counts the hooks current up to the tick when a callback ran or our input went out, never an event's own stamp, so a forward-dated event cannot hide lagging hooks.
- **Denial of service (pointer hook):**
  - A panic in the engine or the callback is caught before it reaches Windows; events then pass untouched, and the engine lets go once. Only the engine's fall asks for a turn, so a fault that recurs never loops.
  - After that one release the host drops the engine, so the mouse module resets its modes and tells the user, and one tap starts it again (`kx-mod-mouse.md`).
  - The host keeps its own fixed record of the buttons and keys its sent input holds down, sized by the port's `MAX_HELD_KEYS`. When the engine is done (it panicked, even in its `release`) and when the host stops, it sends an Up or KeyUp for each one still held.
  - The host also notes the hand's presses that passed untouched, and when the engine drops the release of one (a Grab pick-up with no latch), that press joins the record. So the host's own let-go sends its Up even when the engine's `release` panics (`a_carried_press_is_let_go_by_the_host_even_when_the_engines_release_panics`, property check `nothing_the_hand_let_go_stays_down`).
  - A user's own Up or key-up that reaches the OS untouched clears that entry once our press is proven ahead of it. While our press may still be out (sent and not settled, even after its wait was given up, or in doubt), the record keeps it and the next batch starts with an owed Up, which a new press of that button or key by the user cancels.
  - Each turn, release, stop and reinstall sends its input as one batch, and each act carries its own id, so its echo settles it and every older act still out; an older act whose echo never came is a gap and shifts no later match. The hand's input waits for an echo of the newest batch, which proves all of it passed (`a_swallowed_echo_is_a_gap_whose_press_stays_in_doubt_and_shifts_no_later_match`), and a batch sent with our hooks out, as a reinstall's, settles at once (`a_reinstalls_batch_sent_with_the_hooks_out_is_settled_at_once`).
  - A wait given up after `echo_ms` keeps its acts out, so a late echo settles only its own act and never ends a newer batch's wait, even for an act the room dropped (`a_given_up_batchs_late_echo_settles_only_its_own_acts`, `the_oldest_acts_make_room_and_a_late_echo_of_one_ends_no_newer_wait`). A press whose echo never came, or that the oldest acts dropped to make room for a batch, stays in doubt until its own echo or an owed Up.
  - The callback never waits or allocates: the engine's buffer is reserved once, and acts past the room are dropped and logged at the stop, counts only. The queue is bounded: moves coalesce into the newest, and buttons and keys keep a headroom of their own, so they stay in order.
  - When even the headroom is full, events pass without the engine, and it lets go at the next turn. A hand's Up that went ahead of its press, still queued, ends the queue's own batch, so no button stays held; the same holds for a broken engine.
  - Windows drops a hook that answers late; the health check puts it back after the engine lets go, once two checks in a row saw lag. The hook thread runs one step above normal priority, so this is less likely under load.
  - Our own sends count as seen, and input on another desktop (the secure desktop, the lock screen) is not lag there nor at the first check back, so neither puts the hooks back.
  - Dropping a run sends the release before it removes the hooks and waits at most the hook's `STOP_WAIT`; past that, the dropping thread removes them itself and warns. Another program's `WM_QUIT` to the hook thread is ignored.
  - `WAKE` and `WM_QUIT` are posted only while `LIVE` holds the run's thread id, and `WM_QUIT` not once that thread ended. A start that times out sets the stop and posts `WM_QUIT` to a thread that answered late, and a refused health timer logs one warning.
  - `release_now` (the app's panic hook) has the hook thread send the queue, the engine's release and what the record still holds, and keeps the hooks and the run, so a panic the kernel catches never ends mouse assist. It waits at most `RELEASE_WAIT` and returns at once on the hook thread; a let-go message nobody in the process asked for does nothing.
- **Elevation (libraries):** `dll::pin` limits libraries named without a folder to the app's folder and System32, so the working folder and `PATH` can no longer lend one to the uiAccess process. It does not cover the libraries the exe imports, which load before `main`; those must sit beside the exe.
  - The speaker loads `xaudio2_9.dll` itself, from System32 only, at the first play, so it is never an import. `XAudio2` then opens the audio device by COM class activation (the device enumerator) in the uiAccess process, where COM may read a per-user `HKCU` registration first, so P14's Process Monitor check covers its classes (`keyxtend.md`, `docs/items/P14.md`).
- **Elevation (focus):** `give_back` moves the focus only from one of our windows to another app's live window. The adapter never asks for the focus for our own windows (ADR-0013); only the spike and the test tools keep such a request.
- **Elevation (shortcuts):** a send names an id, never keys, so it sends only what the compiled-in table holds, with the latched scans pressed once around each step. Every step goes in one `SendInput` batch, and every held key is let go after a partial send.
  - Lock PC calls `LockWorkStation`, never an injected Win+L, which Windows ignores. Tests only plan events, never send them or lock the session.
  - The history check (`shortcut::history`) only compares the held scans and the key with the table's chord; it sends nothing (ADR-0034 decision 7).
- **Elevation (power):** the `Power`-gated port only asks `ShutdownWindows` to show Windows' own Shut Down Windows dialog, where the user picks or cancels; no code confirms it, and no test opens it.
  - The shell object (`Shell.Application`) is made in-process (`CLSCTX_INPROC_SERVER`) on the open's own apartment thread and released before COM stops there (`power/win.rs:21-25`), so its class registration loads code into the uiAccess process (see Should fix).
- **Elevation (worker):** the media worker decodes images copied from any app, so it starts with less than we have (ADR-0004, ADR-0034 decision 5).
  - Its token is ours made restricted by `CreateRestrictedToken` (`DISABLE_MAX_PRIVILEGE`, so every privilege but change-notify goes, and Administrators deny-only), then `TokenUIAccess` cleared and the integrity level set to Medium (S-1-16-8192), as a child of a uiAccess process otherwise keeps uiAccess. So even an elevated host starts a worker with no admin group or privilege (`the_token_made_for_the_worker_reads_back_restricted`, `the_worker_token_denies_administrators_alone`).
  - It starts suspended, and the start reads its token's uiAccess, level, groups and privileges back. It ends the worker before its first instruction if it kept uiAccess, runs above Medium, can use Administrators or holds another privilege, even a disabled one it could enable (`the_worker_runs_restricted_without_ui_access_at_medium_integrity`, `a_token_that_keeps_any_right_is_refused`).
  - It inherits only its stdin's read end and its stdout's write end (`PROC_THREAD_ATTRIBUTE_HANDLE_LIST`) and gets no stderr (`the_worker_inherits_only_its_pipes`, which first proves its check sees a handle a plain child inherits).
  - Its job caps its memory at `memory_mb`, takes no second process, ends it on a crash without an error box, and ends it when our last handle closes, so it dies with us (`the_job_caps_the_worker_alone_in_it`, `the_job_ends_the_worker_when_its_host_lets_go`).
  - Its job also bars it from shared UI: other programs' windows, the clipboard, global atoms, desktops, display and system settings, and signing out, none of which a decoder needs (`the_job_bars_the_worker_from_shared_ui`).
- **Elevation (reveal):** Open folder asks the running Explorer's desktop window for its shell object (`ShellWindows`, `CLSCTX_LOCAL_SERVER`) and has it `ShellExecute` the folder with the `open` verb and no arguments. With the system's registration of that class, nothing starts as our child and the window keeps Explorer's rights, never our uiAccess or integrity (ADR-0034); a per-user override is left to P14's check (see Should fix).
- **Denial of service (worker):** a hung, crashed or lying worker costs one draw's `deadline_ms`, is ended, and starts again only after a growing backoff (`kx_platform::pictures`). Asks are written on a thread of their own, so a worker that stops reading cannot hold the host past the deadline.
- **Information disclosure (box watch):** it reads only when a module that holds `ReadFocusedText` asks, at most the words asked and `read_chars` characters before the caret.
  - It never reads a password box (UI Automation's `IsPassword`, or an edit class with the style bit `field.toml` names). It never reads an unknown box either: a fact it cannot read, a class `field.toml` lists as opaque (remote desktops, virtual machines, terminals, game engines), or a read-only box.
  - A watch whose COM, client or handler fails tells Unknown once, and its reads answer `Unavailable`. Dropping the run takes the module's callback away under its lock, so nothing is told after the drop.
- **Denial of service (box watch):** reads run on the watch's own thread, each within `read_ms`, and `watch` never waits for that thread to start, so a hung app stalls no key and no frame.
- **Information disclosure (key guard):** DPAPI ties the data key to this user's logon secret, so another user or PC normally gets `Refused`; how strong that is depends on the account (see Accepted). Programs running as this user can still unwrap it.
- **Tampering (packs):** while a pack is mapped, its file cannot be opened for writing, renamed or deleted, as it is shared for reading only. A pack holds no user data, and its reader must treat it as untrusted bytes.
- **Elevation:** injection runs only on a module's call through the `InjectInput`-gated port.
  - The Keys route types exactly the text or sends nothing, checked exactly only on the golden layouts, where dead keys are known (see Should fix). Ctrl-only and Alt-only answers are refused, a line feed is typed as Enter, not Ctrl+Enter, and every key is checked against the layout before the send.
  - Every `unsafe` block is scoped and has a `// SAFETY:` comment. It touches only locals, our own token, handles we close, Windows-allocated strings freed once, the message structs Windows passes our window procedure, the event structs it passes our hook callbacks, the procedure kept in our window's property (see Accepted), the shell object `power` makes and releases on the open's own thread, plain calls with no pointer (`LockWorkStation`, `GetKeyboardLayout`), or, in the speaker, the `XAudio2` library it loads from System32 and never frees, the factory pointer cast to its declared signature, the engine and voices we made and our static samples. The clipboard part reads clipboard memory only while the clipboard is open and the memory locked, never past its `GlobalSize`, frees memory `SetClipboardData` refused, and reads version information only through offsets checked against its own buffer; P8's worker start touches only our token, its copy and the worker's, the worker's pipe ends, job and process and an attribute list kept until deleted, the disk and calendar parts only locals Windows fills, and the reveal only the Explorer objects it holds on its own COM thread.
  - The focus handler (`field/focus.rs`) has no hand-written `unsafe`: an inner module's allow covers only the handler's struct and the COM glue windows-rs's `implement` macro writes for it.

### Should fix (tracked issue)
Dead key then Space (P14, fix before beta): a dead key is checked by the character `ToUnicodeEx` gives for it alone, which holds on the EN, FR and AR golden layouts. On others a dead key and Space may type another character (Swiss French ¨ gives ", Czech ˙ gives ·), so the Keys route may type that instead (`docs/items/P14.md`).

A cut send after a dead key (P14): after a cut Keys-route send that follows a dead key's press, `deliver` releases the keys still down but never sends the Space, so the dead key stays pending (`docs/items/P14.md`).

Uncapped lift-backs (P13): the guard lifts a dropped window back every time, so a program that keeps dropping our window holds it in a loop; each lift is one `SetWindowPos` that never moves or activates it. The cap needs a `[ui]` setting, which P13 adds (`docs/items/P13.md`).

A stale focus token (P13): `give_back` checks only that the noted window lives, and the token is taken once at start, so hours later a reused handle could get the focus (`docs/items/P13.md`).

Done (P7, Task 13): `InputInjector::text` builds two inputs per UTF-16 unit in one batch, whatever the length. The port still takes any length, but its one caller, the keyboard, sends one key's text or a picked word within `[keyboard] text_cap` characters (`kx-mod-keyboard.md`).

The power dialog's COM class (P14): each Power click makes `Shell.Application` in-process in the uiAccess process, so P14's check that no per-user `HKCU` class registration loads there must cover it too (`keyxtend.md`, `docs/items/P14.md`).

P14's check must click Open folder and also plant an out-of-process override (`LocalServer32`, `TreatAs`), not only in-process ones (`docs/items/P14.md`).

Done (P8, hands-on check, 2026-10-31): on the signed dev install, running at High with uiAccess, `g20 worker` read a running worker at Medium without uiAccess. The start's own read-back of groups and privileges, which ends a worker that keeps any right, let it run.

Done (P3, ed424ef): the tray's class reader sliced its buffer by Windows' count inside a callback, where a panic would abort the uiAccess process. It now reads with `get`, as the other readers do.

Done (P4 review, 28766d8, 14d8003, bfb0cde, 3255dae): one echo could end the wait for several batches, our own sends and other desktops read as lag, a timed-out start left its thread running, and a release could pass our unproven press. Each is fixed as the pointer-hook threats above say.

### Accepted (with reason)
`QueryPerformanceCounter` cannot report failure through `Clock::now`; Windows XP and later never fail it, so the clock reads the result as given.

`SHGetKnownFolderPath` in the `windows` crate drops the out-string on failure without `CoTaskMemFree`; Windows returns no string then, so nothing leaks in practice.

Another program can put our tags (`TAG`, `REPLAY`) on its own input so that our hooks skip it. The tags only keep us from acting on our own input; it is not a trust boundary, and forging it only hides that input from KeyXtend.

`ToUnicodeEx`'s no-state-change flag needs Windows 10 1607 or later, and builds before it are long out of support; on them, reading a dead key could leave it waiting in our own thread only.

`caps_on` reads Caps Lock with `GetKeyState`, the spike's method, which is this thread's view of the toggle. The P3 hand check confirmed that it follows a press outside the non-activating keyboard; the keyboard's relabel tick redraws on that change.

Windows does not report input that UIPI blocks (a window above our integrity level), so `SendInput` may count it as sent. The uiAccess build is allowed to reach those windows, which is why the app runs with uiAccess.

`kx-target-window --layout` (a test tool, never shipped) activates a layout, which on Windows 8+ switches the whole session's input language. It puts the previous layout back on close, only while it holds the keyboard, and when the switch does not take; a killed window cannot.
- Gates bring it to the front, then close it with `WM_CLOSE`; a failed restore logs `# layout-kept`, which G26 reports.
- G26 is the only gate that passes `--layout`, and it runs on the GitHub runner only, never on the owner's PC.

Another program in this session can create `Local\KeyXtend.Running` first, so KeyXtend reads a copy as running and then finds no command window. A named object cannot be kept from a same-user program; the next copy then stops after its tries and says another copy did not answer (`keyxtend.md`).

DWM may draw Mica and Acrylic as a solid colour on an inactive window, and the keyboard is never active. The manual look check (G13) decides; the spike's undocumented accent-policy blur ended in P3.

A monitor whose DPI Windows cannot give reads as 96, so a window there may be sized as if unscaled until the next reading.

The guard calls the procedure kept in its window property (`KeyXtend.Guard`). Another process's `SetPropW` passes UIPI only at our integrity level or above, and such a program can already write into our process.

`inject::send`, `input`, `send_keys` and `vk_key` are public for the gate tools, and `send` takes raw inputs with any tag and no recovery. Modules cannot depend on the adapter (tidy), and the app never calls them.

The host's record of held input counts a hand's press that our input replayed, such as a held press that Right-click lets through. The hand's own Up clears it, but only once our press is proven ahead of it.
- So a replayed press the hand still holds is let go at a stop or when the engine is done, which can end that drag. That is the safe side: a missed Up would leave the button down.
- Another program that forges our `REPLAY` tag can end the echo wait early, and then a hand's Up can clear the record while our press is still in flight. That button of ours may then stay down past a stop, which is accepted because a program that can inject input could already hold a button down itself.

When every echo of our newest batch is lost (another program swallowed them, or Windows dropped a hook), the hand's input waits `echo_ms` for that batch once, and nothing stays down.

The record of the hand's presses is not cleared when Windows drops the hooks, so a release the hooks missed leaves it stale, and an Esc or a Grab toggle while the user still holds the picked-up press leaves that press recorded. The next let-go may then send one stray Up, never a Down and never a stuck button, which at worst ends a drag the hand holds then.

A panic inside a hook callback runs the app's panic hook there, which lets go first, as `release_now` returns at once on the hook thread, then writes one log line with only the panic's place. It comes once per run in practice, as the panicking engine is then given up.

A hook thread that misses its stop wait is left running after its hooks are removed; it holds only the engine until the process ends, and a later start reads `Busy`.

A speaker thread that misses its stop wait is left running; once its audio call returns, it finishes that one ask, serves no more, drops its voices and engine and ends.

A starting worker's two pipe ends are inheritable until `CreateProcessAsUserW` returns. Our own starts name their handles, but a plain `std::process::Command` started on another thread at that moment inherits every inheritable handle and could hold the worker's pipe open. Tidy F4 bans `std::process::Command` and `QProcess` in product code, so the app starts no process that way. A raw `CreateProcess*` call with `bInheritHandles` = TRUE elsewhere would get past F4; today `worker/start.rs` is the only product code that starts a process (the reveal asks the running Explorer), and none uses `std::process::Command`.

A UI Automation call to a stuck app holds every UI Automation call in the process until its timeout, `read_ms`, so the scroll pad's end check reads unknown that long. Windows marks an app hung only after 5 s, so the run pings the target at each aim, turn and reach instead: from the last ping it answered until the next goes unanswered, one turn's interval plus `read_ms` at most, a few turns may still queue for a busy app.

Typed text is not zeroised: one click's text (at most `layouts::KEY_TEXT_UNITS` UTF-16 units) or one picked word (at most `[keyboard] text_cap` characters) lives for one send, and Windows keeps its own copies in the input queue.

The DPAPI entropy is in the program, so any program running as this user can unwrap the data key. DPAPI normally guards against other users and other PCs (but see the blank-password case below), not the user's own programs (spec §9.1). Such a program can also forge sealed blobs that pass the tag, so predict's decoders treat every blob as untrusted (`kx-mod-predict.md`).

A UI Automation provider that ignores `GetText`'s max length hands over its whole text, which becomes a `String` before the `read_chars` cut. The string is in our process already, and only memory is at stake.

The opaque classes in `field.toml` are known names (remote desktops, virtual machines, terminals, game engines). A remote desktop or terminal whose class is not listed reads as Text, so its words may be read and learned; P7's hands-on check tries a terminal and a remote desktop.

A read moves back by the provider's own word unit, so an app whose units differ may hand over fewer or more words; `last_words` still keeps at most the words asked, and `read_chars` bounds the read.

A program that mapped a pack writable before we opened it, then closed its handle, could still change the bytes under our read-only view. The pack reader must therefore never trust an offset or a length from a pack.

On a local account with a blank password, DPAPI's master key has no secret behind it, so anyone with offline access to an unencrypted disk can unwrap the data key. Disk encryption is the user's protection there.

A copy whose app renders it only when asked (delayed rendering) makes `GetClipboardData` wait on that app, so a hung app can hold the watch thread past `open_ms`. Every clipboard reader shares this; the watch thread does nothing else, so typing and the panel go on.

Dropping the watch waits `STOP_WAIT` for a thread such an app holds, then warns and leaves it to end alone; that thread may still tell its one copy after the drop.

The cap bounds what we copy and hand on, not the copy Windows makes: to size a format, `GetClipboardData` brings it into our process before `GlobalSize` can be read, so every format sized, up to and including the one that passes the cap, costs its memory once. Formats after that one, and a picture beside text, are never fetched; a picture beside a file list is fetched, though the files decide the entry's kind.

A password manager that marks nothing is read like any copy; the spec's follow-the-clear and `skip_apps` cover it in the module. A Unicode file list is the only kind read: a 16-bit era ANSI list is left out, as no current app writes one.

The live clipboard tests write the real clipboard and lose what the user had copied, so they run only when `KX_LIVE_CLIPBOARD=1` is set at build time (`build.rs`), as CI's Windows job does, and are ignored otherwise. They write only test text, keep it out of Windows' history and cloud, and never show another app's copy.

A drive letter mapped to a share, such as `Z:\`, is an absolute drive path, so `probe_ok` lets it through and the file check reaches the share (builder's call). Telling it apart needs the drive's type, a later change; the files thread is never joined, so a slow share holds only its rows' sizes.
