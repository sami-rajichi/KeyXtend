# Security note: kx-platform-windows

- **Owner:** product owner
- **Last review:** 2026-10-14
- **Status:** Reviewed
- **Scope:** `crates/kx-platform-windows`: the QPC clock, the program and per-user folders, COM start-up, the uiAccess check, where libraries load from (`dll`), input injection (`inject`, `strokes`, `keys`), layout reading and the switch request (`layouts`, `langinfo`), the app in front (`front`), the window guard and window queries (`window`), screens (`screen`), the system look and its watcher (`sysui`, `watch`), DWM backdrops (`backdrop`), the graphics adapter the UI draws on (`gpu`), the one running copy with its command window (`instance`, `hidden`), the tray icon with its window and front-window hook (`tray`), the heaps' free pages after a look change (`memory`), the mouse and keyboard hooks that host the hold engine (`hook`), and the speaker on `XAudio2` (`sound`). It runs inside the uiAccess `keyxtend` process.

## Threats (STRIDE-lite)
- **Spoofing:** a shell or parent process could set `LOCALAPPDATA` or `TEMP` to aim our data elsewhere. Mitigation: the folder comes from the known-folder API, not the environment.
- **Tampering:** our own injected input could loop back through our own hooks (P4) and be acted on twice. Mitigation: every event carries `keys::TAG` (the keyboard) or `keys::REPLAY` (the hold engine) in `dwExtraInfo`, and our hooks never act on either, except our keyboard's `TAG` Esc, which only cancels a carry; the tags are pinned by a test.
- **Logging / repudiation:** `PlatformError` never holds a path, and `InjectError` holds only counts. The injector, the layout source and the window, look, tray and memory parts log nothing; the pointer hook logs only counts, never a point or a key (a panic in its callback: see Accepted); the speaker logs only a warning kind, an HRESULT or a wait in ms, never a clip; `UiError` holds at most an OS error code, and the debug output of key events and decoded keys never shows a key or unit. Layout names and characters are not typed text, but a caller must never log `Scan` values next to what the user typed.
- **Information disclosure:** no network; nothing leaves the process. Text is read only through `Redacted::expose` to build the send.
- **Denial of service:** start-up fails with a typed error, never a panic, when Windows refuses the clock or a folder. After a partial send it tries to release every key still held, and once more one event at a time for what Windows refuses, so no modifier should stay stuck down; a mask key (`keys::MASK_VK`, unassigned) goes first when Alt or Win is released, so neither opens the menu bar or Start. The speaker's queue is bounded (`QUEUE`): a play past it is dropped, so `play` never waits. Dropping the speaker waits at most its `STOP_WAIT` for its thread, then warns and leaves it.
- **Elevation (layouts):** `request` posts only `WM_INPUTLANGCHANGEREQUEST`, with a layout checked against the installed list, to the window that has the keyboard; that window decides whether to switch. With uiAccess the post may reach a window above our integrity level, which is why the port needs `InjectInput`. The adapter never loads, activates, adds or removes a layout; only the test window's `--layout` activates one (see Accepted).
- **Tampering (layouts):** the layout names come from `HKLM`, which only administrators can change; they are display text, bounded and never run or parsed further.
- **Tampering (guard):** the guard puts its procedure in front of visible windows of our own process only, on the thread that owns them (Windows refuses any other). It keeps no global state beyond a per-thread list of the windows it is lifting back, a per-thread recheck flag and its message id, and unhooks itself on `WM_NCDESTROY`, so no procedure outlives its window. A tip's lift (`lift_alone`) moves only visible windows of our process with that title, never activates them and leaves their owners in place, and a guard run's `top` title only changes the order in which it guards those same windows.
- **Tampering (topmost):** another program's `SetWindowPos` that drops a guarded window out of the topmost band (`HWND_NOTOPMOST`, `HWND_BOTTOM`, or after a plain window) is undone at once: the guard lifts it back, with the windows it owns, without activating it. Windows drops an owner with its owned window and may tell only that window, so the guard lifts the furthest guarded owner too (a shadow with its keyboard), then every guarded window that owner owns, each above its owner. It follows only owners it guards on the same thread, so another program cannot draw a window of its own into the lift. A lift made inside another program's call may not land, so the guard posts itself a recheck that runs after the window has answered the move; that program may still be busy then, and a recheck that runs too early is not repeated. A recheck posts none, so the checks always end, and another program that posts it only triggers the same check. The guard calls `SetWindowPos` only on windows of its own thread, though Windows still moves their owner and owned windows with them. Settings is not guarded, so it can still go behind other windows.
- **Denial of service (click-through):** only a window that let clicks through when first guarded (tips, shadows) keeps click-through; on any other, the guard refuses `WS_EX_TRANSPARENT`, so no program can make the keyboard click-through.
- **Spoofing (command window):** the command window is message-only and reachable from this session only: Windows keeps window messages inside one desktop, and UIPI drops posts from a lower integrity level. A post does not name its sender, so the window acts only on a code from the fixed table (`show`, `quit`); a program that can post there runs as this user at our level and could end the process anyway.
- **Denial of service (UI parts):** a panic in a look or command callback is caught before it reaches Windows, and the next change or command is still heard. Another program's `WM_CLOSE`, or a `WM_QUIT` it posts to the window or to its thread, cannot end the command or watch window: the loop ends only on `stop`'s `WM_QUIT`, sent after `stop` sets its flag. Dropping a claim or a watch waits for its thread, and so for a running callback, unless its quit message could not be posted; a callback must never wait for the thread that drops it. A flood of look broadcasts costs one reading each and calls back only on a real change; a failed OS read gives a safe default, never a panic.
- **Spoofing (tray):** the tray window takes the taskbar's callback and `TaskbarCreated` from any program in the session, which UIPI would otherwise drop from below our level; a forged message can only open our own menu or add our icon again. The front-window hook reads class names only, never titles or content, and skips our own windows.
- **Denial of service (tray):**
  - A panic in the tray listener is caught before it reaches Windows.
  - Adds and changes run from the icon's own queue and no lock is held during a taskbar call, so a message that arrives inside the call cannot deadlock the thread, and neither `show` nor `set` waits on the taskbar: a hung Explorer stalls only the icon's thread, never the keyboard. A change queued behind an add, or behind a taskbar restart, follows the add.
  - The icon's thread deletes the icon as its window ends, after any add it had queued, so no dead icon stays behind while the app runs.
  - The front-window hook, the only hook in P3, runs out of context with our process skipped; it reads one class name and queues a wake inside `catch_unwind`, so it cannot stall anyone's input.
- **Spoofing (pointer hook):** another program can put our tags on its input.
  - `TAG` or `REPLAY` hides that input from the engine. A forged `REPLAY` event that matches our next act of its kind ends the wait for our echo early, so the hand's next event may overtake our input; a forged `TAG` event does not.
  - Such a forged echo can also make the record of held input forget a press of ours that is still in flight (see Accepted).
  - A forged `TAG` Esc can only cancel a carry, as the engine hears our keyboard's Esc in the physical mode.
  - `SIM_TAG` acts only in the simulated mode, which exists only in builds with the `sim-input` feature (the gate tool's, never the shipped app). In the physical mode no other injected input acts.
  - The health check counts the hooks current up to the tick when a callback ran or our input went out, never an event's own stamp, so a forward-dated event cannot hide lagging hooks.
- **Denial of service (pointer hook):**
  - A panic in the engine or the callback is caught before it reaches Windows; events then pass untouched, and the engine lets go once. Only the engine's fall asks for a turn, so a fault that recurs never loops.
  - After that one release the host drops the engine, so the mouse module resets its modes and tells the user, and one tap starts it again (`kx-mod-mouse.md`).
  - The host keeps its own fixed record of the buttons and keys its sent input holds down, sized by the port's `MAX_HELD_KEYS`. When the engine is done (it panicked, even in its `release`) and when the host stops, it sends an Up or KeyUp for each one still held.
  - A user's own Up or key-up that reaches the OS untouched clears that entry once our press is proven ahead of it. While our press may still be out (sent and not echoed, or its echo lost), the record keeps it and the next batch starts with an owed Up, which a new press of that button or key by the user cancels.
  - Each turn, release, stop and reinstall sends its input as one batch. Each `REPLAY` echo matches the next act of its kind, so the hand's input waits for the newest batch's first echo, which proves all of it passed, and an older batch's late echo never ends that wait.
  - The callback never waits or allocates: the engine's buffer is reserved once, and acts past the room are dropped and logged at the stop, counts only. The queue is bounded: moves coalesce into the newest, and buttons and keys keep a headroom of their own, so they stay in order.
  - When even the headroom is full, events pass without the engine, and it lets go at the next turn. A hand's Up that went ahead of its press, still queued, ends the queue's own batch, so no button stays held; the same holds for a broken engine.
  - Windows drops a hook that answers late; the health check puts it back after the engine lets go, once two checks in a row saw lag. The hook thread runs one step above normal priority, so this is less likely under load.
  - Our own sends count as seen, and input on another desktop (the secure desktop, the lock screen) is not lag there nor at the first check back, so neither puts the hooks back.
  - Dropping a run sends the release before it removes the hooks and waits at most the hook's `STOP_WAIT`; past that, the dropping thread removes them itself and warns. Another program's `WM_QUIT` to the hook thread is ignored.
  - `WAKE` and `WM_QUIT` are posted only while `LIVE` holds the run's thread id, and `WM_QUIT` not once that thread ended. A start that times out sets the stop and posts `WM_QUIT` to a thread that answered late, and a refused health timer logs one warning.
  - `release_now` (the app's panic hook) has the hook thread send the queue, the engine's release and what the record still holds, and keeps the hooks and the run, so a panic the kernel catches never ends mouse assist. It waits at most `RELEASE_WAIT` and returns at once on the hook thread; a let-go message nobody in the process asked for does nothing.
- **Elevation (libraries):** `dll::pin` limits libraries named without a folder to the app's folder and System32, so the working folder and `PATH` can no longer lend one to the uiAccess process. It does not cover the libraries the exe imports, which load before `main`; those must sit beside the exe. The speaker loads `xaudio2_9.dll` itself, from System32 only, at the first play, so it is never an import.
- **Elevation (focus):** `give_back` moves the focus only from one of our windows to another app's live window. The adapter never asks for the focus for our own windows (ADR-0013); only the spike and the test tools keep such a request.
- **Elevation:** injection runs only on a module's call through the `InjectInput`-gated port. The Keys route types exactly the text or sends nothing, checked exactly only on the golden layouts, where dead keys are known (see Should fix): Ctrl-only and Alt-only answers are refused, a line feed is typed as Enter, not Ctrl+Enter, and every key is checked against the layout before the send. Every `unsafe` block is scoped, has a `// SAFETY:` comment, and touches only locals, our own token, handles we close, Windows-allocated strings freed once, the message structs Windows passes our window procedure, the event structs it passes our hook callbacks, or the procedure kept in our window's property (see Accepted).

## Findings
### Must fix (blocks Definition of Done)
Done (P3 review): typed text was classed Secret, which asks for zeroising that the send path does not do. It is Sensitive, as in the keyboard and `kx-ui` notes, and Accepted says why it is not zeroised.

Done (P4 review, 3362cd4): an engine that panicked was kept but never called again, so its module never learned and its keys stayed lit. The host now drops it after its one release.

### Should fix (tracked issue)
Dead key then Space (P14, fix before beta): a dead key is checked by the character `ToUnicodeEx` gives for it alone, which holds on the EN, FR and AR golden layouts. On others a dead key and Space may type another character (Swiss French ¨ gives ", Czech ˙ gives ·), so the Keys route may type that instead (`docs/items/P14.md`).

A cut send after a dead key (P14): after a cut Keys-route send that follows a dead key's press, `deliver` releases the keys still down but never sends the Space, so the dead key stays pending (`docs/items/P14.md`).

Uncapped lift-backs (P13): the guard lifts a dropped window back every time, so a program that keeps dropping our window holds it in a loop; each lift is one `SetWindowPos` that never moves or activates it. The cap needs a `[ui]` setting, which P13 adds (`docs/items/P13.md`).

A stale focus token (P13): `give_back` checks only that the noted window lives, and the token is taken once at start, so hours later a reused handle could get the focus (`docs/items/P13.md`).

Text of any length (P7): `InputInjector::text` builds two inputs per UTF-16 unit in one batch, whatever the length. P3 sends one key's text, at most 32 units; cap it from the settings schema before P7 types words (`docs/items/P7.md`).

Done (P3, ed424ef): the tray's class reader sliced its buffer by Windows' count inside a callback, where a panic would abort the uiAccess process. It now reads with `get`, as the other readers do.

Done (P4 review, 28766d8, 14d8003, bfb0cde, 3255dae): one echo could end the wait for several batches, our own sends and other desktops read as lag, a timed-out start left its thread running, and a release could pass our unproven press. Each is fixed as the pointer-hook threats above say.

### Accepted (with reason)
`QueryPerformanceCounter` cannot report failure through `Clock::now`; Windows XP and later never fail it, so the clock reads the result as given.

`SHGetKnownFolderPath` in the `windows` crate drops the out-string on failure without `CoTaskMemFree`; Windows returns no string then, so nothing leaks in practice.

Another program can put our tags (`TAG`, `REPLAY`) on its own input so that our hooks skip it. The tags only keep us from acting on our own input; it is not a trust boundary, and forging it only hides that input from KeyXtend.

`ToUnicodeEx`'s no-state-change flag needs Windows 10 1607 or later, and builds before it are long out of support; on them, reading a dead key could leave it waiting in our own thread only.

`caps_on` reads Caps Lock with `GetKeyState`, the spike's method, which is this thread's view of the toggle. The P3 hand check confirmed that it follows a press outside the non-activating keyboard; the keyboard's relabel tick redraws on that change.

Windows does not report input that UIPI blocks (a window above our integrity level), so `SendInput` may count it as sent. The uiAccess build is allowed to reach those windows, which is why the app runs with uiAccess.

`kx-target-window --layout` (a test tool, never shipped) activates a layout, which on Windows 8+ switches the whole session's input language. It puts the previous layout back on close, only while it holds the keyboard, and when the switch does not take; a killed window cannot.
- Gates bring it to the front, then close it with `WM_CLOSE`; a failed restore logs `# layout-kept`, which G26 reports.
- G26 is the only gate that passes `--layout`, and it runs on the GitHub runner only, never on the owner's PC.

Another program in this session can create `Local\KeyXtend.Running` first, so KeyXtend reads a copy as running and then finds no command window. A named object cannot be kept from a same-user program; the next copy then stops after its tries and says another copy did not answer (`keyxtend.md`).

DWM may draw Mica and Acrylic as a solid colour on an inactive window, and the keyboard is never active. The manual look check (G13) decides; the spike's undocumented accent-policy blur ended in P3.

A monitor whose DPI Windows cannot give reads as 96, so a window there may be sized as if unscaled until the next reading.

The guard calls the procedure kept in its window property (`KeyXtend.Guard`). Another process's `SetPropW` passes UIPI only at our integrity level or above, and such a program can already write into our process.

`inject::send`, `input`, `send_keys` and `vk_key` are public for the gate tools, and `send` takes raw inputs with any tag and no recovery. Modules cannot depend on the adapter (tidy), and the app never calls them.

The host's record of held input counts a hand's press that our input replayed, such as a held press that Right-click lets through. The hand's own Up clears it, but only once our press is proven ahead of it. So a replayed press the hand still holds is let go at a stop or when the engine is done, which can end that drag. That is the safe side: a missed Up would leave the button down. Another program that forges our `REPLAY` tag can end the echo wait early, and then a hand's Up can clear the record while our press is still in flight. That button of ours may then stay down past a stop. This is accepted because a program that can inject input could already hold a button down itself.

A panic inside a hook callback runs the app's panic hook there, which lets go first, as `release_now` returns at once on the hook thread, then writes one log line with only the panic's place. It comes once per run in practice, as the panicking engine is then given up.

A hook thread that misses its stop wait is left running after its hooks are removed; it holds only the engine until the process ends, and a later start reads `Busy`.

A speaker thread that misses its stop wait is left running; once its audio call returns, it finishes that one ask, serves no more, drops its voices and engine and ends.

Typed text is not zeroised: one click's text, at most 32 UTF-16 units, lives for one send, and Windows keeps its own copies in the input queue.
