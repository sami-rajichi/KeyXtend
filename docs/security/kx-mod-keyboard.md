# Security note: kx-mod-keyboard

- **Owner:** product owner
- **Last review:** 2026-10-26 (P7 security review: hidden marks in picked words, and what guards the erase; the paced erase, stopped by a click away)
- **Status:** Reviewed
- **Scope:** `crates/kx-mod-keyboard`, which runs inside the uiAccess `keyxtend` process from P3 on.

## Capabilities
| Capability | Why needed | What breaks without it |
|---|---|---|
| `InjectInput` | It gates the four services typing needs: `InputInjector` (send keys and text, name the app in front), `LayoutSource` (Caps Lock, whether a key types), `Layouts` (the table shown) and `Shortcuts` (the layer's shortcuts, with the latches held). It also gates the bus events `AssistToggle`, `LatchesChanged`, `LatchesUsed` and `LatchesAsk`. | The module does not start. |
| `KeyboardUi` | It gates the `KeyboardFace` service the module provides, which the ui draws and clicks through, and a provider must hold its service's gate (ADR-0033). | The module does not start (`without_keyboard_ui_it_cannot_offer_the_face`). |
| `ReadFocusedText` | It gates `Typed` and `TypingMode`, which the module tells, and `TypingModeAsk` and `TypeWord`, which it hears (ADR-0033). | The module does not start (`without_read_focused_text_it_cannot_hear_picked_words`). |

- Besides its settings, the module writes only its own `size`, `x`, `y` and `placed`.

## Data handled
| Data | Class (Secret/Sensitive/Public) | Stored where | Encrypted | Retention |
|---|---|---|---|---|
| `[keyboard]` settings: size, place, modifiers mode, language-key style, key repeat, bubble corner, `key_apps`, shortcut pages, `text_cap`, `erase_gap_ms` | Public | `settings.toml` (only the user's changes) | No | Until the user changes them |
| The board: rows, widths, scan codes, roles | Public | Compiled into the app (`board.toml`) | No | The build |
| The text of each click, built from the layout table | Sensitive (typed text; may be part of a password) | Memory only, as `Redacted<String>`, until the injector takes it; not zeroised (`kx-platform-windows.md`) | No | One click |
| Typing state: the latched modifiers and the dead-key wait | Sensitive together with the clicks around it (the latches alone show on screen and to screen readers) | Memory only; kept across a module restart | No | Until a click lets go of it, or the app quits |
| The app in front's file name, for `key_apps` | Sensitive (shows what the user runs) | Memory only | No | One click |
| The shortcuts layer: shown or not, its page, and the shortcut ids the platform knows, with each one's key names for its tip | Public (on screen and in tips) | Memory only; the page is kept across a restart | No | Until the app quits |
| The latched set on the bus (`LatchesChanged`), for modifier + click | Sensitive together with the clicks around it | Memory only; heard only by modules granted `InjectInput`; its debug output shows only a count | No | Until the next change |
| The held key's id and its next repeat time | Sensitive together with the clicks around it | Memory only (`Repeat`) | No | Until the pointer lets go or leaves, the keyboard hides, the list opens, a repeat fails, is stale or types nothing, the next press, or a restart |
| Typed pieces (`Typed`: text, `Erase`, `Advance`, `Break`) | Sensitive (typed text) | Memory only: typing's list under the face's lock, texts in `Redacted`, then one bus event each, heard only by modules granted `ReadFocusedText` | No | Until told, once and in order |
| The typing mode (`TypingMode`: Shift, Caps Lock, a shortcut latch, a waiting dead key) | Sensitive together with the clicks around it | Memory only; heard only by modules granted `ReadFocusedText` | No | Until the next change |
| A picked word (`TypeWord`: an erase count and a text) | Sensitive (it may be a learned word or email) | Memory only, as `Redacted<String>`, until the injector takes it | No | One word |

Typed text never leaves the click or picked word that makes it: it is not stored or logged, and goes only to the injector and, as `Typed` pieces, to modules granted `ReadFocusedText`. Debug output hides scan codes, text, legends, shortcut ids and key names (`Route`, `Plan`, `Legend`, `Layer`, and the port's `ShortcutId` and `KeyName`) and the typing state (`Typing`, `Latches`, `LegendMods`, `KeyState`, `StateView`, and `Repeat`, which shows only its phase), since a run of clicks would show what was typed (ae6f192, d3b925e).

## Inputs from outside (files, IPC, OS callbacks, clipboard, network)
| Input | Validation | Size/time limit | Fuzzed |
|---|---|---|---|
| `[keyboard]` settings | `deny_unknown_fields`; choices by name; sizes finite; `size_min` and `size_max` within `SIZE_FLOOR` (0.8, where key cells on the 31 px row stay at least 24 px apart, WCAG 2.2 SC 2.5.8 through its spacing exception) and `SIZE_CEILING` (4.0); `size` and the rising presets inside `size_min..=size_max`, the step above 0 and no wider than that range; `relabel_ms` from 50 to 10,000 ms (`RELABEL_MS`); `repeat_delay_ms` from 300 to 3,000 ms and `repeat_every_ms` from 33 to 1,000 ms (`REPEAT_DELAY_MS`, `REPEAT_EVERY_MS`); no blank app names; shortcut pages of well-formed ids, at most `MAX_PAGES`, none empty or past the layer's room, no id twice, and an id the platform lacks skipped at start; `text_cap` within `TEXT_CAP`, whose floor fits predict's longest word with chips (`MAX_WORD`) and its gap; `erase_gap_ms` from 0 to 50 ms (`ERASE_GAP_MS`) | Checked at load: a refused value goes back to its default with the `settings-reset` notice. The kernel caps the settings file (`MAX_FILE_BYTES`) | No |
| `board.toml` | Compiled in, never read from disk; `deny_unknown_fields`, rows span the grid, whole columns, unique ids, roles fit; a broken board stops the module with an error, never a panic | Fixed at build time | Property tests |
| Screens, pointer points and the resize corner's overhang from the UI | Integer maths saturates; a place off every screen goes home; a zero or odd DPI or screen never panics; an overhang below 0 or not a finite number counts as none | — | Property tests |
| Key ids from the UI | Looked up on the board, or among the layer's keys while it shows them; an unknown or hidden id is `UnknownKey`, never a panic. While the layer shows, a tap, press or hold on a side key it hides, or on the pad, is `UnknownKey` too, so a stale click where Power was never asks for the dialog | — | Property tests (runs of clicks); `a_tap_press_or_hold_on_a_side_key_the_layer_hides_or_the_pad_is_no_key` |
| Face actions from the UI: panel keys, rows per page, list and preset indexes | A panel key must have a `nav` on the board; zero rows count as one; an index past its list is `NoChoice`; while the list is open its keys are never typed | — | Property tests (list moves) |
| Held-key actions from the UI: `press`, `tick`, `let_go`, `leave` (spec §4.6) | A pressed or let-go key must be on the board (`UnknownKey`, which changes nothing); a press types once, a tick types only while a key is held and a repeat is due, and a late tick types once; a let-go types nothing | One repeat per `repeat_every_ms` (33 ms or more) | Property tests (`Repeat` runs; face runs of presses, ticks, let-gos and leaves) |
| Bus events from the mouse module: `AssistChanged`, `LatchesUsed`, `LatchesAsk`, `PointerPressed` | Plain flags with no payload to check; the latch events need `InjectInput` to send, and `PointerPressed` is ungated. A forged `LatchesUsed` can only let latches go or stop a lone Win press, `AssistChanged` only lights or dims (`dim`) two keys, and a forged `PointerPressed` only stops a picked word going out | — | Thread runs (latches told newest last); both start orders, one with the mouse module already running (`a_mouse_module_already_running_lights_the_keys_at_start`) |
| Bus events from the scroll module: `ScrollChanged` (P5) | Plain flags and a direction, ungated like the pad's own `ScrollTap`, `ScrollStop`, `ScrollPeek` and `ScrollAsk`. A forged `ScrollChanged` only lights or dims the pad, and the pad's clicks still need the user | — | Both start orders, one with the scroll module already running (`a_scroll_module_already_running_lights_the_pad_at_start`); a module that answers a tap at once (no deadlock) |
| Bus events from the power module: `PowerChanged` (P6) | A plain flag, ungated like `PowerAsk` and the keyboard's own `PowerAsked`. A forged `PowerChanged` only lights or dims the Power key; `PowerAsked` goes out only on the user's click while the power module is live, and the system's dialog asks the user again | — | Both start orders, one with the power module already running (`a_power_module_already_running_lights_the_key_at_start`) |
| `TypeWord` from the bus (P7, gated by `ReadFocusedText`) | Types nothing while Ctrl, Alt or Win is latched (or `AltGr` acts as Right Alt), while a dead key waits, when it asks for nothing, when its text holds a hidden character (`kx_module_api::is_hidden`: controls, `HIDDEN_MARKS` and `INVISIBLE`), when its erase count or text passes `text_cap` characters, when the board has no erase key, or while the module is stopped. Else it taps Backspace `erase` times, stopping at the first refused tap and waiting `erase_gap_ms` after each one on the sender's thread, outside the face's lock, then types the text by the route a letter takes now, and tells both as `Typed`. The keyboard does not check `erase` against what it typed: the prediction module's pick check asks the box first, and a click outside our windows heard while the word goes out (`PointerPressed { ours: false }`) stops the rest at once, so the pauses cannot carry the erase to a caret the user moved. Only the latches and dead-key wait at the word's start count, so one clicked during it neither stops it nor is spent by it | `text_cap` characters each way, one word per event; at most 50 ms per Backspace | Unit tests (`tests/keyboard/picked.rs`); thread runs of taps and words at once (`words/threads.rs`) and a click during the wait (`words/gap.rs`); a click away, a latch or a dead key during a pause (`words/during.rs`) |
| Layout tables, Caps Lock and the app name from the ports | Read as data; a missing key goes as its scan code, with every latch held; while the shown table lags the app in front, a scan-code click sends nothing, the face refreshes the layouts once, and the user clicks again | One click | Golden-table tests; a property run of the dead-key wait |

## Threats (STRIDE-lite)
- **Spoofing:** no IPC or network. A key acts on a click or a UI Automation Invoke from any program UIPI lets through, and the face cannot tell who sent it; P3's manual check confirmed that a normal program's click and Invoke type nothing in the signed uiAccess build (test report 2026-10-12, row 11).
  - Only a module granted `ReadFocusedText` can send `TypeWord` (see Accepted), and only one granted `KeyboardUi` can reach the face.
- **Tampering:** a hand-edited value is checked, and a bad one resets alone (kernel repair). Sizes stop at `SIZE_FLOOR` and `SIZE_CEILING`, so a hand-edited size can neither shrink the keys past clicking nor open the keyboard off every screen, and a place off every screen brings the keyboard back to the bottom centre.
  - The shortcut pages name ids only, never keys, so a tampered file can only pick among the shortcuts the platform's own table sends.
- **Logging / repudiation:** the module never logs; a held key's failed repeat, or a shortcut that did not all go out, is one `keys-not-sent` notice, which kx-ui's hub also logs as one warning, with no key. Typed text that reached a log through a field named for it is redacted (the app's log test), and `kx-review` check 4 refuses a `tracing` call on an input path that could carry it.
- **Information disclosure:** the settings are not sensitive; typed text is `Redacted` and never logged. The face's debug output shows no key, place or typing state.
  - `Typed`, `TypingMode` and `TypeWord` name `ReadFocusedText`, so only the keyboard, predict and the ui hear them (`read_focused_text_goes_only_to_the_keyboard_predict_and_the_ui`). A board key's `tell` shows only board data in debug output.
  - A piece the app refused is never told, and Caps, latches and side keys tell nothing.
- **Denial of service:**
  - A size or time of zero or not-a-number is refused, so nothing divides by zero or spins; a relabel time or size past its ceiling is refused, so the labels never stall and the keyboard never opens far off every screen.
  - A stale click is never replayed, so a lagging table cannot loop.
  - A click holds the face's lock while it sends, but no OS call on that path sends a message to another window, so a hung app cannot stall a click. A shortcut's path is the same: plain layout queries, `SendInput`, or `LockWorkStation`, which only starts the lock and returns.
  - A held key repeats at most once a beat, and a late tick types once and never catches up, so a slow frame cannot flood the app.
  - A picked word waits at most `erase_gap_ms` (50 ms or less) per Backspace, on the prediction thread and never under the face's lock, so clicks and the UI go on during the wait (`a_picked_word_waits_on_the_senders_thread_and_leaves_the_face_free`).
- **Elevation:** input goes only through the `InputInjector` and `Shortcuts` ports, and only for a click on a board key or a layer cell, a board key held down, or a `TypeWord` that a chip click asked for; nothing types on its own. With Ctrl, Alt or Win latched (or `AltGr` acting as Right Alt), or on a dead key, a held key types once, so a shortcut such as Ctrl+W never fires many times. A shortcut cell sends only its id and the latched scans to the `Shortcuts` port, once per click, and the platform's compiled-in table picks the keys; a held one never repeats (`holding_a_shortcut_cell_never_repeats`).
  - The keyboard stays the only typist (ADR-0033): a picked word goes through the same route, latches and dead-key rule as a letter, within `text_cap`, and never while a shortcut latch would turn it into shortcuts (`ctrl_alt_or_win_latched_refuses_the_word_whole`). A click outside our windows during its pauses stops the rest of it (`a_click_outside_our_windows_during_a_pick_stops_the_rest_at_once`).
  - A layer key acts only while the layer draws it (`run/layer.rs`, `planned`), and the board refuses ids kept for the layer (`BoardError::Reserved`), so a stale click on a turned page or a hidden layer is `UnknownKey`.
  - The Next key keeps one cell, and the Shortcuts key its own, so a double click on either never lands on a shortcut such as Lock PC.
  - Power publishes `PowerAsked` only while the power module says it is live (`face/bus.rs`, `power`); it sends nothing to the app and keeps the latches.
- **Stuck repeat:** a burst ends on let-go wherever the pointer is, when Qt takes the press away or the keyboard hides or stops (the UI sends `leave`), when the list opens, when a repeat is stale, empty or fails, on the next click (a burst left open, as after a window rebuilt for a lost graphics device), and on a restart. A face property run shows that no tick types and no latch stays down after a let-go or leave, and the UI's hold timer runs only while the face says it holds a key, on a shown keyboard with no list open.
- **Lone press:** a `lone` latch (Win) sends its key alone only on the user's own second click with nothing used since the first; refused whole it stays latched, and taken in part it lets go, so it never goes twice. It holds no other latch, and they then let go as after any key, so in `release` none rides into Start.
- **Stuck modifiers:** latches are the module's state, never held keys; each chord presses and releases its modifiers in one batch, and the platform sends a shortcut's keys, every step, in one batch too (`kx-platform-windows.md`). A send refused whole changes no state; one taken in part uses the latches, so a retry never repeats a modifier. During a burst the latches stay latched, not pressed, and let go when it ends.

## Findings
### Must fix (blocks Definition of Done)
- **Who can press a key (manual check):** only UIPI keeps a normal program from making the uiAccess keyboard type into an admin window, since a key acts on any click or Invoke Windows lets through. P3's manual check confirmed it in the signed build: a normal program's `SendInput` and Invoke typed nothing, and its `SetWindowPos` was denied (test report 2026-10-12, row 11).
- Done (P3, c163124 and 5dcce0e): `size_max`, `size` and `size_step` had no ceiling, so a hand-edited `size_max = 1000` opened the keyboard off every screen on each start. `SIZE_CEILING` and `SIZE_FLOOR` now bound every size at load.
- Done (P7, B10 review): the pause after each Backspace let a click in the app move the caret before the rest of a pick went out, so it could erase other text. A click outside our windows now stops the rest at once (`a_click_outside_our_windows_during_a_pick_stops_the_rest_at_once`).
### Should fix (tracked issue)
- None open.
- Done (P7 fix pass): a picked word was refused only for control characters, so a word forged in a sealed blob could type bidi marks or separators its chip did not show. The keyboard now refuses every `is_hidden` character, and predict drops decoded words the learning rule refuses.
- Done (P7, ADR-0033): `KeyboardFaceKey` carried no capability, yet a `Tap` types, as do `Press`, `Tick` and `LetGo`. It now needs `KeyboardUi`, which only the ui, the keyboard and the mouse module hold (`keyboard_ui_goes_only_to_the_ui_the_keyboard_and_the_mouse_module`).
- Done (P7, Task 13): the debug-only `FaceAction::FlipCaps` is gone, so the face's actions no longer depend on the build kind; the churn flips Caps Lock through a debug wrapper of the layout source (ADR-0033 decision 5).
- Done (P3, cc31ec9): the dead-key wait had no property test; a run of clicks on French AZERTY now pins how the wait starts, ends and stays, and that each Unicode send equals the key's legend without its ◌.
### Accepted (with reason)
- **A front layout that is not installed:** the table shown stands, so a character key sent as a scan code types in the app's own layout and may not match its legend. Telling the user is later work; nothing is typed that the user did not click.
- **`AltGr` as Right Alt:** on a layout without `AltGr` characters, `AltGr` is Right Alt, so a character key runs an Alt shortcut (such as Alt+Y on a dialog) while its legend shows the letter. Ctrl, Alt and Win latches do the same and the key stays lit, as a physical right Alt does.
- **Check, then send:** the stale check and the send are separate OS reads, so a layout switch in the microseconds between them types in the new layout. Only the user's own hotkey or another program can switch then.
- **The dead-key wait is a guess:** a dead key used up elsewhere leaves the wait set. The next character then goes as a key press, which the stale check keeps equal to its legend.
  - The wait also outlives a focus change, so `TypingMode` keeps saying a dead key waits and the chip lane stays empty in the new box until the next key.
- **A click in the same instant as a part:** the stop waits for the mouse module's press event, which comes just after the app took the click, so at most one more Backspace or the text may go after it. With the mouse module off, or prediction wanting no presses, nothing stops a word; prediction wants them whenever a pick replaces text, and its own box check stays.
- **Who may ask for a word:** any module granted `ReadFocusedText` may send `TypeWord`: predict, and the ui, whose hub sends only `ChipPicked` and `WordsAsk` (`kx-ui.md`). Every module is first-party, and each word still passes every check above.
- **No log of picked words:** a refused word is normal (a latch held), and the crate has no logger, so neither a refusal nor a typed word is logged; predict counts its sends.
- **No cap on a burst:** a held key repeats for as long as it is held, as the owner wants, and every way the press ends stops it.
- **A burst follows a focus change:** if another window comes to the front mid-burst, the repeats go to it, as a physical key does.
- **Power's cell under the layer:** while the layer shows, Power's cell holds Next, or a single page's 14th shortcut. A click meant for Power then turns the page or sends that shortcut, whose icon shows there while the Shortcuts key is lit.
- **Lock PC asks nothing:** it locks at once, as Win+L does. KeyXtend cannot type on the lock screen, so signing back in with a password takes Windows' own on-screen keyboard from the sign-in screen's Accessibility button.
- **Shortcuts reach elevated windows:** with uiAccess, Close window or Task Manager act on an admin window in front, as a physical key would; each needs the user's click on its cell.
