# Security note: keyxtend (the app)

- **Owner:** product owner
- **Last review:** 2026-10-26 (P7 security review: what the sealed tag defeats, the set-aside rule and the crates P7 ships)
- **Status:** Reviewed
- **Scope:** `apps/keyxtend`: the command line, the one running copy as the app uses it, the start and stop order, the log subscriber, the panic hook, the mouse hook it hands the mouse module, the scroll target it hands the scroll module, the shortcuts it hands the keyboard, the power dialog it hands the power module, the box watch, word packs and sealed store it provides for word prediction (`words.rs`), the clipboard services, sealed shelf and history folder it provides for the clipboard history (`clip.rs`, P8), the gate-only build, the manifest and Qt's start. The release build is the uiAccess process; the adapters, the kernel and the modules have their own notes.

## Capabilities
| Capability | Why needed | What breaks without it |
|---|---|---|
| Builds the kernel's policy: each shipped module gets exactly what its manifest declares | Only the app knows which modules it ships and vouches for them | A module that needs a grant fails at load and offers Try again |
| Provides the platform's `ScrollTarget` under `ScrollTargetKey`, gated by `Scroll` (P5, ADR-0029) | Only the scroll module declares `Scroll`, so the target reaches it alone (`the_scroll_target_reaches_only_the_scroll_module`), as the mouse hook reaches only the mouse module | Without the `mod-scroll` feature the target is still provided but no module can reach it, and the pad dims |
| Provides the platform's `Shortcuts` under `ShortcutsKey`, gated by `InjectInput` (P6, ADR-0031) | Only the keyboard requires it, for the shortcuts layer (`the_shortcuts_reach_the_keyboard_whose_layer_sends_them`); a module must also hold `InjectInput` to reach it | The keyboard does not start |
| Provides the platform's `PowerDialog` under `PowerDialogKey`, gated by `Power` (P6, ADR-0031) | Only the power module declares `Power`, so the dialog reaches it alone (`the_power_dialog_reaches_only_the_power_module`); the keyboard only asks over the bus. `mod-power` is a default feature (`every_module_feature_is_on_by_default_the_scroll_and_power_ones_too`) | Without the `mod-power` feature, or with `power` in `[kernel] disabled`, the dialog is still provided but no module can reach it, and the Power key dims |
| Provides the platform's `FieldWatch` under `FieldWatchKey`, gated by `ReadFocusedText` (P7, ADR-0033) | Only the keyboard, predict and the ui hold `ReadFocusedText`, so only they may require it (`the_box_watch_reaches_only_the_modules_that_read_typed_text`, `read_focused_text_goes_only_to_the_keyboard_predict_and_the_ui`); only predict does | Without `mod-predict`, or with `predict` in `[kernel] disabled`, the watch is provided but nothing watches |
| Provides the platform's `WordPacks` under `WordPacksKey`, with no gate (P7, ADR-0032) | Packs are public seed data, read from the folders `words::pack_dirs` names; only predict requires them | A pack that is missing or does not read leaves the lane with learned words only, and `notice.words-missing` names a shipped language |
| Provides one `SealedFiles` under `SealedStoreKey`, gated by `SecretStore` (P7) | Predict and, from P8, the clipboard declare `SecretStore`, and the store reaches only them (`the_sealed_store_reaches_only_the_secret_store_holders`); it seals in `SEALED_DIR` under the data folder, with the platform's key guard. `mod-predict` is a default feature (`mod_predict_is_a_default_feature_and_the_default_build_ships_predict`) | A store the OS cannot unlock keeps learned words in memory for the run, with `notice.words-locked` |
| Provides the platform's `Clipboard` under `ClipboardKey`, gated by `ReadClipboard`, and `ClipboardWriter` under `ClipboardWriterKey`, gated by `WriteClipboard` (P8, ADR-0034) | Each reaches only its gate's holders (`the_clipboard_watch_reaches_only_the_read_clipboard_holders`, `the_clipboard_writer_reaches_only_the_write_clipboard_holders`), and only the clipboard module requires them. `mod-clipboard` is a default feature (`mod_clipboard_is_a_default_feature_and_the_default_build_ships_it`) | With `clipboard` in `[kernel] disabled`, nothing watches, reads or draws (`with_the_clipboard_switched_off_nothing_watches_reads_or_draws`) |
| Provides one `SealedShelfFiles` under `SealedShelfKey`, gated by `SecretStore` (P8) | It reaches only the clipboard and predict (`the_sealed_shelf_reaches_only_the_secret_store_holders`); it seals in `<data>/clipboard` (`clip::CLIP_DIR`), made at boot, with a key file apart from the learned words' (`the_history_and_the_learned_words_keep_their_keys_in_folders_apart`) | A shelf the OS cannot unlock fails the clipboard's start, and the kernel offers Try again |
| Provides `Pictures` under `PicturesKey` (ADR-0034) and `Calendar` under `CalendarKey` (P8), with no gate | Pictures are drawn by `keyxtend-worker` beside the program, which the adapter starts with lowered rights (`kx-platform-windows.md`); the calendar gives only the local time | The clipboard module does not start without them; a worker that fails leaves each row its type icon |
| `ReadClipboard` and `WriteClipboard` in the policy (P8, ADR-0034) | `ReadClipboard`: the clipboard, the keyboard and the ui; `WriteClipboard`: the clipboard and the keyboard (`the_clipboard_gates_go_to_the_clipboard_the_keyboard_the_ui_and_predict`) | A module without them cannot hear copies, drive the panel or make the keyboard paste |
| `KeyboardUi` in the policy (P7, ADR-0033) | It gates the face and the pointer notes; only the ui, the keyboard and the mouse module declare it (`keyboard_ui_goes_only_to_the_ui_the_keyboard_and_the_mouse_module`) | A module without it cannot reach the face or hear the notes |
| uiAccess (release manifest only, `asInvoker`) | Stay above the Start menu and type into windows above our integrity level | UIPI drops keys sent to elevated windows, and the keyboard hides under the Start menu |

| Learned words and emails, and their wrapped data key (P7) | Sensitive (the key Secret) | `SEALED_DIR` under the data folder (ADR-0015), one sealed store for the folder (`kx-crypto.md`) | Yes | Until replaced, forgotten or the data folder is deleted |
| The clipboard history and its wrapped data key (P8) | Sensitive, at times Secret (the key Secret) | `<data>/clipboard`, made at boot so Open folder always opens, one sealed shelf for the folder (`kx-crypto.md`, `kx-mod-clipboard.md`) | Yes | `[clipboard]`'s limits; pinned entries until unpinned |

## Threats (STRIDE-lite)
- **Spoofing:** a later copy speaks only through the adapter's command window, which acts on its fixed codes.
  - A same-user program that holds `Local\KeyXtend.Running` without a command window makes the next copy stop with "another copy runs but did not answer", after its tries; it never starts a second keyboard. Each try claims again first, so a copy that quits meanwhile leaves the session to the new one.
- **Tampering:** the QML, fonts and icons are compiled in (see `kx-ui.md`); the command line is refused unless it is exactly one known flag, or, in the gate-only build only, `--sim-input` alone or before `--show`.
  - The word packs are files beside the program, so whoever can write that folder can change the seed words; every pack passes `Pack::parse` and holds no user data (`kx-mod-predict.md`). An installed copy's folder is writable by administrators only.
  - A changed or swapped sealed file fails its tag and is set aside (`kx-crypto.md`), unless a program running as this user unwrapped the key and sealed it. A blob that opens but does not read is copied to its aside blob by predict before any save (`kx-mod-predict.md`).
- **Logging / repudiation:**
  - The log opens after the kernel loads its settings and before any module starts; when they did not load, the kernel's defaults open it, so a failed boot is logged. If the file cannot open, the app logs to standard error and says so once.
  - A later copy never opens the log, since opening sets the running copy's log aside; its refusals go to standard error only.
  - The panic hook replaces Rust's default one. It first calls the adapter's `release_now`, so a panic during a Grab carry never leaves a button down (`tests/quiet.rs` checks it lets go before it logs).
  - Only then does it log the file, line and column, never the payload, which could hold typed text; until the log is set up it also writes the place to standard error.
  - The hook lets go and keeps running, so a panic the kernel catches never ends mouse assist. `release_now` waits at most the adapter's `RELEASE_WAIT`, and returns at once on the hook's own thread, where the callback's own recovery lets go.
  - The first line gives the version and whether uiAccess is on; the last says the app ended.
- **Information disclosure:** nothing is sent anywhere; `cargo tree -p keyxtend` holds no network, TLS or media crate (ADR-0004), and tidy D7 refuses kx-theme's `files` feature, its asset and WAV readers, in the app's normal tree, so the uiAccess app links no media parser.
  - P6 added no outside crate: `kx-mod-power` is the lock file's one new package, and the adapter's new `serde` and `toml` were already in the app's tree.
  - P7 adds `kx-crypto` with RustCrypto's `chacha20poly1305` and the crates under it (`chacha20`, `poly1305`, `aead`, `universal-hash`, `cipher`, `inout`, `hybrid-array`, `crypto-common`, `typenum`, `cpufeatures`, `block-buffer`, `ctutils`, `cmov`), `zeroize` and `getrandom`, `fst` for the packs' lexicon, and `windows-core` in the adapter; none reaches the network, and `THIRD_PARTY.md` records each.
  - The stage copies into `PACK_DIR` the packs the source index lists, the index and the credit files, and its words check refuses a stage that lacks one or holds any other file there. It holds the download, measured deflated, to `[workspace.metadata.stage] max_mb`, and the installed size to `[workspace.metadata.devtools] install_max_mb` (`dev-tools.md`).
  - The app makes one `SealedFiles` for its data folder, as two stores over one folder could race on the key file (`kx-crypto.md`).
  - P8 adds `kx-mod-clipboard` and `kx-ipc`, both ours. The worker's `png` and the crates under it stay out of the app's tree (`nothing_the_app_builds_with_reaches_a_decoder_or_the_worker`), and tidy D4 bans `png` and `fdeflate` there.
  - The app makes one `SealedShelfFiles` for `<data>/clipboard`, apart from the words' folder, and hands the ui that folder for Open folder (`open_folder_shows_the_history_folder_under_the_data_folder`).
  - Qt's network library loads only because Qt Qml and Qt Quick import it: the stage check refuses any other importer and every TLS plugin, and a `kx-ui` test keeps network addresses and `XMLHttpRequest` out of the app's QML.
- **Denial of service:**
  - Quit ends the request queue; the kernel's thread stops the modules, then ends the UI even if stopping panics (a drop guard). After Qt's loop, `drain::stop` removes the tray icon and joins the thread, whether it was running, already asked to quit, or ended in a panic.
  - Quitting while the pad scrolls stops the scroll module, which closes its run and hides the outline, and the mouse hook lets go (`quitting_while_scrolling_closes_the_run_hides_the_outline_and_lets_the_hook_go`).
  - The tray icon goes when the app ends or a panic unwinds. A panic inside a Qt callback aborts the process, and a killed process leaves the icon until the pointer passes over it, as Windows does for any app.
  - `--quit` with no copy running starts nothing and exits at once.
  - A same-user program that squats the running mutex can keep KeyXtend from starting (Accepted).
- **Elevation:** a uiAccess process can drive elevated windows, so nothing another program of the user controls may load code into it.
  - One cfg, `kx_ui_access`, which `build.rs` sets together with the manifest's uiAccess, turns on the pinning below, so they cannot drift apart. A second, `kx_no_console`, hides the console in every release build, the gate-only one too, and so holds the first; tests read the built exe's manifest and subsystem.
  - The uiAccess build calls `SetDefaultDllDirectories(APPLICATION_DIR | SYSTEM32)` first in `main`, so a library named later without a folder never comes from the working folder or `PATH`.
  - The exe's own imports (Qt's DLLs, the MSVC runtime) load and set up before `main`, by Windows' standard order, which includes the working folder and `PATH`. The stage check holds each import in the stage or System32, and shipping the runtime is P14's (`docs/items/P14.md`).
  - Every build clears Qt's variables before Qt starts, through `qunsetenv`, by the names in the C runtime's narrow copy of the environment, which Qt's byte reads use; `qunsetenv` clears each from the wide copy, which Qt's text reads use, too.
  - The narrow copy converts names with the ANSI code page's best fit, so a Win32 name such as `ＱＴ_PLUGIN_PATH` reads there as `QT_PLUGIN_PATH`; Rust's `remove_var` changes only the Win32 copy and is unsafe in edition 2024, which the app forbids. Clearing them also keeps a global `QT_SCALE_FACTOR` from skewing the keyboard's DPI layout.
  - The manifest also names the UTF-8 code page (`activeCodePage`, Windows 10 1903 and later), so in the app that copy holds each name exactly and none narrows to a Qt one; the walk over narrow names still covers a Windows that ignores it. A test reads both from the built exe.
  - The clearing runs on the main thread after the adapter's threads start: Windows locks both environments, and no thread of the app writes them.
  - The uiAccess build pins Qt's plugin folders to the app's folder, and the QML imports to the compiled-in modules and the app's `qml` folder; each module's plugin still loads from beside its `qmldir`. Debug builds use the installed Qt.
  - The manifest asks for uiAccess only in release, with `asInvoker`, PerMonitorV2 and the UTF-8 code page; the linker writes no import library or exports file (`/NOIMPLIB /NOEXP`). The app's code forbids `unsafe`; the hardening calls live in `kx-platform-windows` and in a `kx-ui` bridge.

## Gate-only input
- **What:** the `gate-input` feature turns on the adapter's `sim-input` and adds `--sim-input`, with which the mouse engine acts on the gate tool's tagged input instead of the hand's (ADR-0027 decision 3). The run logs one warning that it is a gate build.
- **Why it never ships:** in the uiAccess app, any program of the session could send that tagged input and steer our clicks into admin windows. The feature is off by default, and nothing in the workspace turns it on.
- **How it is enforced:** the stage check (`cargo xtask stage`, and `dev-install` on an app folder) refuses a program that holds the flag's text (`[workspace.metadata.stage] gate_flag`, which the app's agree test pins), and `dev-install` refuses to sign any exe that holds it. The gate build's warning logs the flag as a field, which keeps its text whole in a release exe, and a test reads the built exe: only the gate build holds the flag.

## Findings
### Must fix (blocks any signed build)
- Done (fix round 1): Qt's environment could load a same-user program's plugin or QML module into the uiAccess process. Every Qt variable is now cleared before Qt starts, and release builds pin Qt's plugin and import folders.
- Done (fix round 2): a name the ANSI code page narrows to a Qt variable (a fullwidth `ＱＴ_`, or a best-fit last letter) escaped the clearing, which read the Win32 names. The clearing now walks the C runtime's narrow names, which Qt's byte reads use, and the manifest names the UTF-8 code page outright.
- Done (fix round 1): libraries named without a folder could come from the working folder or `PATH`. Release builds now load them only from the app's folder and System32.
- Done (fix round 1): Qt Quick read and wrote a shader pipeline cache in a user-writable folder. It is now turned off.
### Should fix (tracked issue)
Only the staged uiAccess build runs the pinned paths. Task 20 checked its stage (`cargo xtask stage`), and ran a scratch copy of it whose manifest alone had uiAccess off, since Windows starts no unsigned uiAccess program outside Program Files:
- Done (Task 20): every library the exe and each staged plugin import, the MSVC runtime too, is in the stage or System32. The stage check walks their import tables and fails on any other, and the running copy loaded each one from there, with Qt's own folder first in `PATH`.
- Done (Task 20): Qt's plugins are in subfolders of the app's folder (`platforms/`, `imageformats/`) and its QML modules in `<app>/qml`, each module's plugin beside its `qmldir`; the release app loaded `main.qml` with the pinned lists.
- Done (Task 20): with `QT_PLUGIN_PATH`, `QT_QPA_PLATFORM_PLUGIN_PATH`, `QML_IMPORT_PATH`, `QML2_IMPORT_PATH` and fullwidth aliases (`ＱＴ_PLUGIN_PATH`, `ＱＴ_QPA_PLATFORM_PLUGIN_PATH`, `ＱＭＬ2_IMPORT_PATH`) planted, the app loaded nothing from their folders.
- Done (Task 20): copies of `Qt6Svg.dll`, `Qt6Network.dll` and `d3dcompiler_47.dll` in the working folder were never loaded.
- Done (Task 20): `%LOCALAPPDATA%\KeyXtend` (shader and `.qmlc` caches) was never created; the copy wrote only its portable log.
- Open (P14): typing under the planted variables, since a test click would move the owner's mouse; nothing loading from them is confirmed above.
- Open (P14): the MSVC runtime is not staged and loads from System32, where the Visual C++ redistributable puts it. On a PC without it Windows would look in the working folder and `PATH`, so the installer must provide it.
- Open (P14, before any signed build leaves the development PC): COM may read a per-user registration (`HKCU\Software\Classes\CLSID`) before the machine's for a process that is not elevated, and a uiAccess process is not. On the staged signed build, list the in-process classes it activates (Process Monitor) and check that a planted `HKCU` override for each never loads (`docs/items/P14.md`).
  - The speaker adds such classes from P4 on: `XAudio2` opens the audio device by COM class activation (the device enumerator) in the uiAccess process at its first sound, and the key sound is on by default.
  - The Power key adds one from P6 on: each click makes `Shell.Application` in-process (`CLSCTX_INPROC_SERVER`) on a short apartment thread of the uiAccess process, so the trace clicks Power too (`kx-platform-windows.md`).
  - Open folder adds one from P8 on: it activates `ShellWindows` as a local server, whose calls load proxy and stub classes in-process, so the trace clicks it and also plants an out-of-process override (`LocalServer32`, `TreatAs`).
- Open (P14): pin the QML disk cache off in the uiAccess build, with Qt's own cache option in `harden_qt` and a stage check that refuses `.qml`, `.js` and `.mjs` files (`docs/items/P14.md`).
- Open (P14, `kx-release`): a panic inside a dependency logs that dependency's source path as the build machine saw it, which the binary also holds and which can name the builder's account. Release builds trim or remap those paths (`docs/items/P14.md`).
### Accepted (with reason)
- A same-user program can squat `Local\KeyXtend.Running`: a named object cannot be kept from the same user. A normal program cannot end the uiAccess process itself, but it can start `keyxtend.exe --quit`, so squatting gives it nothing more.
- Commands that arrive before the hub exists wait in an unbounded list: only same-session programs can post them, one code each, during the few milliseconds of load.
- Lines the kernel logs while it loads are lost, since the log opens from the loaded settings; their notices still reach the banner.
- `Qt6Network.dll` loads in the uiAccess process because Qt Qml and Qt Quick import it (ADR-0013). No TLS backend ships, the stage check lets only those two import it, and the app's QML names no network address (`kx-ui` offline test).
- In the release build standard error goes nowhere, so a refused argument or a later copy's failure is silent there; the running copy's log is never touched by a later copy.
- Variables from `HKCU\Environment`, or any a parent passes, reach the process. Every Qt name is cleared, `PATH` and the working folder reach only the exe's own imports, Qt reads `LANG` only as a locale name, and `__COMPAT_LAYER` applies only Windows' own shims.
- Fonts from outside the bundle: Native asks Windows for Segoe UI by name, and Qt falls back to the system's fonts for a glyph no theme font has. Windows also reads per-user fonts (`%LOCALAPPDATA%\Microsoft\Windows\Fonts`) and per-user GPU shader caches in every process of the user, elevated ones too, so the uiAccess process adds no new path; whether Qt's font list takes per-user fonts is not yet checked (P14, `docs/items/P14.md`).
- Any program of the session can start `keyxtend.exe --show` or `--quit`, since a uiAccess program starts without a prompt. Show only shows the keyboard, and Quit only ends it.
- One `SecretStore` gates both the word store and the clipboard's shelf, so predict and the clipboard could each require the other's service. Each keeps its own folder and key file, and a gate per store would need a new ADR (Ruling 46).
- The keyboard and the ui could require the clipboard services their gates allow, not only the events ADR-0034 names; neither does, and the keyboard already sends input. A service-only gate would need a new ADR (Ruling 48).
