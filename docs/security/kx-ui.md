# Security note: kx-ui

- **Owner:** product owner
- **Last review:** 2026-10-26 (P7 fix pass: hidden marks in picks, and the stopped lane)
- **Status:** Reviewed
- **Scope:** `crates/kx-ui`: the texts, the `[ui]` settings, the `ui` module and its hub, and the QML module `KeyXtend.Ui` with its cxx-qt bridges. It runs inside the uiAccess `keyxtend` process, with the bridges on the Qt GUI thread.

## Capabilities
| Capability | Why needed | What breaks without it |
|---|---|---|
| `KeyboardUi` | It gates the `KeyboardFace` service the module requires and the `AssistNote` and `PointerMoved` events the hub hears (ADR-0033). The module only draws; it sends keys through the face, never through `InputInjector`. | The `ui` module fails and offers Try again (`without_keyboard_ui_it_cannot_get_the_face`); the rest keeps running. |
| `ReadFocusedText` | The chip lane: the hub hears `Suggested` and sends `ChipPicked` and `WordsAsk` (ADR-0033). It requires no `FieldWatchKey`, though this gate would let it. | `Hub::listen` fails, so the app does not start (`without_read_focused_text_the_hub_neither_hears_nor_sends_the_lane`). |
| `KeyboardFace` service (required) | The board, the live state, every click on a key, and the language of the layout shown, which the keyboard's texts follow (ADR-0020). | The `ui` module fails and offers Try again; the rest keeps running. |
| UI ports the app hands in (`WindowGuard`, `Screens`, `SystemLook`, `Backdrop`, `Tray`, `Memory`, `Speaker`) | No-focus guard, window shape and a tip's lift, the keyboard's entry watch and the outline laid under the keyboard (P5), screen areas and the pointer, the system look, the backdrop, the tray icon, giving the heaps' free pages back after a look change (ADR-0023), and the key and mouse sounds. | The windows take focus, the look stops following Windows, a hidden keyboard has no way back but a second start, look changes keep freed memory committed, or nothing sounds. |

Log lines name only `[ui]` keys, counts and OS error codes; no line holds a pointer point or a box, and neither `assist_json` nor `scroll_json` is ever logged (`no_log_line_holds_a_box_or_a_point`).

## Threats (STRIDE-lite)
- **Spoofing:** the QML files, the bundled fonts and the icons are compiled into the binary as Qt resources, so a file swapped on disk cannot change a window. The hub adds a theme's fonts to Qt's font list only from those resources, never from a user path (ADR-0021). Native's Segoe UI and Qt's glyph fallback come from Windows' font stack (`keyxtend.md`, Accepted). Every text is drawn as plain text, so a translation, a layout name or a chip cannot add rich text or links. The objects QML makes reach only the hub the app installed once.
  - The hub sends picks and menu taps only through its restricted handle, so even a bug there cannot publish an event gated by a capability the ui does not declare, such as `InjectInput`.
- **Tampering:** a hand-edited `[ui]` value that fails the check never reaches the look or the timers; only that key goes back to its default.
- **Logging / repudiation:** errors name setting keys, OS codes and counts, never key ids or text (`Redacted<T>` is not needed because nothing sensitive is logged). A refused icon names its id, which holds only our own icon name and tint.
  - Steps from QML that do not read log one fixed line, never the JSON or a key name (`bridges/ui/texts.rs:70`).
- **Information disclosure:** notice arguments are bounded setting names, counts and language names, with no bidi marks around them (ADR-0022). List items, text arguments, chip texts, email rows and the OS names on the space bar and in the language list lose their control characters, line breaks and bidi controls first (`kx_module_api::is_hidden`), so a crafted setting key, layout name or learned word can neither split a text nor turn it around. A pick of a word holding such a mark types nothing, as the keyboard refuses `is_hidden` too (`kx-mod-keyboard.md`), so what a chip shows is what types.
- **Denial of service:**
  - The hub never holds its lock during a face, port or waker call, so an adapter thread cannot deadlock the Qt thread.
  - Quit, from the user or a second copy, ends the request queue, so the app's drain thread cannot keep a hidden uiAccess process alive; when that thread is gone, Quit ends the UI itself.
  - Guard tries stop at `guard_tries` per run, and equal notices are merged.
  - The overlay's bus handlers only store and wake, and its wake is never queued twice before QML reads, so a moving pointer cannot flood the Qt thread (`tests/hub/assist/props.rs`). The scroll state's wake works the same way (`tests/hub/scroll/props.rs`).
  - The scroll outline's four edge windows exist only while the hub names a box, and are freed after it. Each is click-through (`Qt.WindowTransparentForInput`), takes no focus (`Qt.WindowDoesNotAcceptFocus`, never `requestActivate()`), joins the guard's quiet run and lies just under the keyboard (`layUnder`), so it never covers a key or takes a click meant for the app.
  - A sound is a send to the speaker that never waits. The key sound reads only whether an action is a tap or a press, never its key, and no play logs; `[ui] sound_volume` and `sound_idle_ms` stay within their ranges in `settings.rs`.
  - The heaps' free pages go back once after a look change, or once for back-to-back changes, after every shown window dropped its cached graphics, never at idle; a refused give-back warns once and stops nothing (ADR-0023).
  - A second copy's tries to reach the running one stop at `send_tries`, `send_wait_ms` apart; `settings.rs` bounds each timing and count.
  - `tray_hide` on `quitAsked` removes the tray icon for good; a picture drawn later cannot bring it back, so no dead icon stays in the taskbar.
  - A lost graphics device, or a window whose scene graph cannot start, ends Qt's loop once and brings the windows back at most `[ui] device_rebuilds` times per run (0 to 10), so neither can loop. Past that, a loss leaves each window its own device, and a window that still cannot draw ends the app with one error and a failure code, where Qt would end it with no word. Each try at a new device counts, `device_retry_ms` (at most 5 s) apart; a timer times the wait, so the GUI thread never sleeps. A frame drawn off the GUI thread ends the sharing for the run, so no later rebuild makes a shared device; nor does one when the drawing variables did not read back. Only debug builds can mark a device lost, a frame off the thread or a window failed.
- **Elevation:**
  - The crate root has `#![deny(unsafe_code)]`; only `src/bridges/` allows it, for the cxx-qt glue and the calls into `cpp/`, and each block has a `// SAFETY:` comment (tidy F3). The windows never take focus: the guard hands the focus back and no bridge activates a window.
  - `harden_qt` keeps another program of the user from loading its plugin, QML module or cached shader into the uiAccess process. It clears every name with a Qt prefix from the C runtime's narrow copy of the environment, which Qt's byte reads use, so a name the code page narrows to a Qt one goes too; `qunsetenv` also clears it from the wide copy that Qt's text reads use. It then turns off Qt Quick's shader cache on disk.
  - It reads that copy without the runtime's lock, which is safe on Windows because nothing writes it while `harden_qt` reads it; the only later writes are the adapter pins of a device rebuild, on the GUI thread. With a folder, it and `pin_imports` limit plugins and QML modules to the app's own folders; `cpp/harden.h` calls only Qt's and the C runtime's own functions.
  - After the clear, `pin_adapter` sets one Qt variable, `QT_D3D_ADAPTER_INDEX`, to the number the Windows adapter picked (the lowest-power GPU), on Qt's thread before Qt starts, so no outside value chooses Qt's graphics adapter. A device rebuild picks it again the same way, never from outside input.
  - `pin_drawing` then sets `QSG_RENDER_LOOP=basic` and `QSG_NO_DEPTH_BUFFER=1` (`harden::DRAW_VARS`), so the one shared `QRhi` is used on the GUI thread only; the app shares it only when both read back through Qt's byte read, as Qt Quick reads them, and makes it only on the thread of Qt's app object (ADR-0021).
  - `pin_timing` then sets four more fixed Qt names, `QT_D3D_MAX_FRAME_LATENCY`, `QT_D3D_NO_VBLANK_THREAD`, `QT_QPA_UPDATE_IDLE_TIME` and `QSG_RENDERER_BUFFER_POOL_LIMIT`, and the default swap interval, from the checked `[ui]` settings: whole numbers within their ranges and two flags, never outside text. The first three default to Qt's own values, the buffer pool to 0 (ADR-0028) and the swap interval to 1 (ADR-0026); an outside value of the same name is cleared first.
  - `Keyboard.drawNow` (`press_frame = "now"`, the default since ADR-0025) sends one update event to our own shown Quick window of that title on the GUI thread, and refuses while that window handles a frame's event or its device records a frame, so no frame starts within another; it reads no key and draws nothing Qt would not draw at its next update.
  - The frame log (`[ui] frame_log`, off by default) logs times only: its watch reads each event's type and a Windows message's id, never a key, a position or text, and the action's marks carry no key id. While on, it logs one info line per frame and per press into the user's log file.

## Findings
### Must fix (blocks Definition of Done)
- None.
### Should fix (tracked issue)
- None open.
- Done (P7, ADR-0033): `KeyboardFaceKey` carried no capability, while `FaceAction::Tap` types keys, so any module that required the face could type. It now needs `KeyboardUi`, which only the ui, the keyboard and the mouse module hold, and the notes and pointer moves name it too.
- Done (P6): `steps_of` (`bridges/ui/texts.rs:67-73`) had no test of its own; its unit tests now show that bad JSON, a wrong shape, a bad or over-long name and deep nesting each give no keys and no panic.
- Done (P3, 4cfa0c8 and 553fa82): a plain `Text` reads markup, and notice arguments carry setting keys from the user-writable file, so rich text could have made the uiAccess process load an image. `tests/texts/markup.rs` now fails on any QML text element that does not read plain text.
### Accepted (with reason)
- The request queue to the app (Try again, Quit) has no bound: only the user's clicks and a second copy's Quit fill it, one request each, and Quit ends it.
- Any program of the session can forge the tray's callback, which the filter lets through for the taskbar, and open our tray menu at a spot it picks. The menu holds only Show keyboard and Quit, which `keyxtend.exe --show` and `--quit` give any program anyway.
- Qt's own messages go to the debugger channel, which a program of the session can read, never to the log file, also for a category the user-writable `qtlogging.ini` turns on. Our windows hold no typed text, and the click positions such logs could show are what that program's mouse hook sees anyway.
- `harden_qt` warns and carries on when a Qt-prefixed name stays set. Qt reads only short fixed names, which `qunsetenv` always clears, so a name left over is never one Qt reads.
- The frame log's press lines keep each press's time, so the gaps between them show the typing rhythm, which can hint at what was typed. The log needs those times to match presses with frames; it is off by default, and its setting says to keep it off while typing anything private (P3 review, 2026-10-12).
- The steps JSON from QML has no length cap: only our compiled-in QML calls `keysTip` and `keysText`, with the board's own steps from the platform's table. `serde_json` reads any text without a panic and stops at its nesting limit.
