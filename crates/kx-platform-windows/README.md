# kx-platform-windows

The Windows adapter: the only product crate that calls Win32 (ARCHITECTURE.md invariant 3). It implements the ports from `kx-platform` and `kx-module-api` on Windows; the app picks it, and modules only ever see the ports.

The crate builds on every system. OS code is Windows-only, and the pure parts (QPC ticks to microseconds, the folder rule, the injection plan and its key tables, the shortcut tables and their plans, the layout reading logic and layout ids, the styles the window guard keeps, box and DPI maths, the graphics adapter pick, system colours, the backdrop table, the command table, the tray's readers, and the scroll pad's wheel steps, routes, fallback, pointer-history and box maths, and the box watch's kind rules and its `field.toml` table, the clipboard's table, markers, format pick, write bytes and file-list reader, and the calendar's tick sums) are tested everywhere. So is the scroll run's aim, turn and reach over a fake desk. So are the pointer hook's rules (whose input the engine hears, the batch, the queue behind our input, the health check, the record of held input and the numbers) and the speaker's (the voice pick, the idle stop, the one rebuild and its thread), over fake systems.

Every guarded window must start topmost. `remember` and `give_back` hand the focus back only from our window to another app's. It needs no timings: the caller retries (`[ui] guard_delay_ms`, `guard_tries`). |

| `WinLook` (`sysui`, `watch`) | `kx_platform::ui::SystemLook` | Dark apps (`AppsUseLightTheme`), the accent pair (`UISettings` `AccentDark1` and `AccentLight2`), the seven system colours while high contrast is on, animations off, the pointer size (`CursorBaseSize`, 32 when missing or outside Settings' 32 to 256), and the display language as a BCP-47 tag (empty when Windows cannot say). | `scroll` | none | The scroll pad's pure rules (ADR-0029), for the scroll target the OS part builds on. `Wheel::per_line` turns a line into wheel delta from the user's wheel settings (`SPI_GETWHEELSCROLLLINES`, or `SPI_GETWHEELSCROLLCHARS` sideways), and none for 0 or a page (`PAGE_SCROLL`). | `WinScroll` (`scroll::{run, ping, win, uia}`) | `kx_module_api::ports::ScrollTarget` | Each run aims at the window under the pointer, or, with the pointer on the keyboard, at the point kept before it entered; while our open list, which pages, shows, it wins the aim whatever point was kept (`Desk::paging`), and that aim carries the list window's box (`GetWindowRect`, no UI Automation) and turns nothing, as the module turns the list's page. ## Capabilities and settings

The adapter holds no capability of its own: the kernel grants capabilities to the modules that use its ports, the injector's, layout source's and shortcuts' service keys need `InjectInput`, `PointerHookKey` needs `PointerHook`, and `PowerDialogKey` needs `Power`; `FieldWatchKey` needs `ReadFocusedText`, and `WordPacksKey` needs none, as packs hold no user data. `ClipboardKey` needs `ReadClipboard`, `ClipboardWriterKey` needs `WriteClipboard`, and `CalendarKey` needs none. It has no settings. The hook's timings come in `HookConfig` from the mouse module's settings and the speaker's voices and idle time in `SpeakerConfig` from the `ui` module; the app folder name is `kx_platform::APP_DIR_NAME`, which also names the running copy's mutex and command window, and the apps that get key presses are the keyboard module's `key_apps` setting. The UI ports are the app's and the `ui` module's, not the kernel's, so they have no service key.

## Features

`sim-input` adds `WindowsPlatform::sim_pointer_hook`, whose engine acts only on the gate tool's `SIM_TAG` input. Only the app's `gate-input` test build turns it on, and `cargo xtask stage` refuses that build (ADR-0027).

## Security

See `docs/security/kx-platform-windows.md`. Every `unsafe` block has a scoped `#[allow(unsafe_code, reason = "...")]` and a `// SAFETY:` comment. The injector and the layout source never log; the injector's errors carry counts, never text, and a switch error names no layout. The window, look and tray parts never log either; a panic in a look, command or tray callback is caught before it reaches Windows. The pointer hook and the speaker log only counts, error codes and waits, never a point, a key or a sample. The scroll target and the entry watch never log a point or a box. The key guard and the word packs never log, and no pack error names a path. The clipboard part logs only a fixed warning when its compiled-in table does not parse, never a part, a path or an app. The box watch logs only fixed warnings, with an error or HRESULT at most, never text or a count of text.
