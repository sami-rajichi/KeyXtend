# kx-platform-windows

The Windows adapter: the only product crate that calls Win32 (ARCHITECTURE.md invariant 3). It implements the ports from `kx-platform` and `kx-module-api` on Windows; the app picks it, and modules only ever see the ports.

The crate builds on every system. OS code is Windows-only, and the pure parts (QPC ticks to microseconds, the folder rule, the injection plan and its key tables, the layout reading logic and layout ids, the styles the window guard keeps, box and DPI maths, the graphics adapter pick, system colours, the backdrop table, the command table, the tray's readers, and the scroll pad's wheel steps, routes, fallback, pointer-history and box maths) are tested everywhere. So is the scroll run's aim, turn and reach over a fake desk. So are the pointer hook's rules (whose input the engine hears, the batch, the queue behind our input, the health check, the record of held input and the numbers) and the speaker's (the voice pick, the idle stop, the one rebuild and its thread), over fake systems.

## What it provides

| Part | Port | What it does |
|---|---|---|
| `WindowsPlatform` | `kx_platform::Platform` | Hands out the clock and the folders; `new` fails when Windows refuses either. `injector()`, `layouts()` and `pointer_hook()` hand out the input injector, the layout source and the mouse hook on the hand's input for the app to register under `InputInjectorKey`, `LayoutSourceKey` and `PointerHookKey`; `sim_pointer_hook()`, only with the `sim-input` feature, hands out a mouse hook on the gate tool's input instead. `scroll_target()` hands out the scroll target for `ScrollTargetKey`. `guard()`, `screens()`, `look()`, `backdrop()`, `instance()`, `tray()`, `memory()` and `speaker()` hand out the UI ports, each as an `Arc<dyn …>` for the app and the `ui` module. |
| `QpcClock` | `kx_module_api::Clock` | Microseconds since Windows started, from the performance counter; the time base `kx-gates` and `kx-target-window` log. |
| `dirs` | `kx_platform::AppDirs` | `exe_dir` is the running program's folder; `user_dir` is `APP_DIR_NAME` inside the Local AppData known folder, never read from environment variables. |
| `WinInjector` (`inject`) | `kx_module_api::ports::InputInjector` | Taps, chords and text for the app in front, in one `SendInput` batch each, every event tagged `keys::TAG`. Text goes as Unicode, or as key presses in the front app's layout (`VkKeyScanEx`, checked with the layout source's `ToUnicodeEx` under the current Caps Lock; Space follows a dead key), or not at all. After a partial send it tries to release the keys still down, with a mask key before Alt or Win. |
| `WinLayouts` (`layouts`) | `kx_module_api::ports::LayoutSource` | Every installed layout (Windows gives the count first, so there is no cap), what each key types per modifier state with `ToUnicodeEx` (which never changes the keyboard state), Caps Lock, and the layout of the window with the keyboard. `request` posts `WM_INPUTLANGCHANGEREQUEST` to that window and never switches anything itself; an uninstalled layout types nothing. The logic runs over a fake OS in tests. |
| `langinfo` | none | A layout's language facts: the ISO code and native name from the locale, right to left from its reading layout, and the layout's English name from the registry (a variant is found by its `Layout Id`). Reading layout ids and Windows' answers is pure. |
| `strokes` | none | The injection plan as plain key events (combos, Unicode units, what is still down), built and tested on every system. Its debug output never shows a key. |
| `keys` | none | The key tables: the tags (`TAG` on the input we inject, `REPLAY` on the pointer hook's input for its engine, `SIM_TAG` on the gate tool's simulated hand), the virtual keys Windows sends as extended, the `VkKeyScanEx` modifier bits and keys, and the keys `ToUnicodeEx` reads held (Caps Lock, `AltGr`, left and right modifiers). |
| `front` | none | The app in front: the window that has its keyboard (`focus`, `focus_of`), that window's layout (`thread_layout`) and its program's file name. Its layout comes from `WinLayouts::foreground`. |
| `inject::{send, send_keys, input, vk_key}` | none | The one `SendInput` path, shared with the test tools and the spike. |
| `layouts::{id, hkl, ask, read_typed, is_printable}` | none | Layout ids to and from Windows handles, the switch request to a given window, and how a `ToUnicodeEx` answer reads, shared with the test tools and the spike. |
| `com::Com` | none | COM start-up for one thread, undone when dropped, for UI Automation and the Windows Runtime. |
| `uiaccess::{active, check}` | none | Whether this process really runs with uiAccess. `check` fails when Windows will not say, so a caller that must fail closed (the gate tool) can refuse; `active` reads that as no. |
| `gpu::low_power_adapter` | none | The lowest-power hardware GPU (DXGI's `MINIMUM_POWER` preference, software adapters skipped) as its place in DXGI's adapter list, the number Qt's `QT_D3D_ADAPTER_INDEX` takes; none when DXGI cannot say, so Qt keeps its own. The app pins it before Qt starts, as the keyboard needs no big GPU. |
| `dll::pin` | none | Limits where libraries named without a folder load from to the app's folder and System32 (`SetDefaultDllDirectories`), for the whole process; the app's uiAccess build calls it first. |
| `WinGuard` (`window`) | `kx_platform::ui::WindowGuard` | Guards our visible windows except the spared one (Settings): it puts its procedure in front of the window's own (`GWLP_WNDPROC`, the original kept in a window property), keeps `WS_EX_NOACTIVATE`, `WS_EX_TOPMOST` and `WS_EX_TOOLWINDOW` in `WM_STYLECHANGING` (and click-through only on a window that had it when first guarded), answers `MA_NOACTIVATE`, keeps every move passive, lifts a window that left the topmost band straight back in `WM_WINDOWPOSCHANGED`, from its furthest guarded owner on the same thread down (a shadow, then its keyboard and the windows it owns, each above its owner), checks it once more from its queue after the window has answered the move (a registered message it posts to itself, which posts no more; one that runs while the other program is still busy is not repeated), and unhooks itself on `WM_NCDESTROY`. Only the thread that owns a window may guard it, and the one titled `top` comes last, so a pop-up shown again lands in front. `shape` sets a window region, which also stops drawing outside it; like backdrops, it is a call for the UI thread. `lift_alone` puts shown windows alone at the top of the topmost band (`SWP_NOOWNERZORDER`), as a tip does when it shows, and `lay_under` puts them just under another of ours, as the outline goes just under the keyboard. `watch_entries` marks the keyboard, a guarded window only: at each entry of the pointer its guard reads `GetMouseMovePointsEx` once and keeps the point before it (`window::entry`), then asks for `WM_MOUSELEAVE` at every move; which move is an entry and when to ask again are pure rules (`window::watch`), tested over random runs. A pointer already on the keyboard when marked makes no entry, a leave under the keyboard's capture keeps the entry, a capture lost off the keyboard ends it, and the kept point goes with the keyboard. Every guarded window must start topmost. `remember` and `give_back` hand the focus back only from our window to another app's. It needs no timings: the caller retries (`[ui] guard_delay_ms`, `guard_tries`). |
| `window::{foreground, from_raw, is_ours, own_windows, own_titled, own_bounds, title, guard_own, guarded, shape, give_back}` | none | The window queries and the guard with a window lifted last, shared with the test tools and the spike. Titles and the guard's mark are read without a message, so any thread, or G9 in another program, may read them. Nothing here asks for the focus for our own windows. |
| `WinScreens` (`screen`) | `kx_platform::ui::Screens` | Every monitor's work area, effective DPI and primary flag, and the pointer; boxes are physical pixels in a per-monitor DPI-aware process, as Qt makes it. `screen::{work_area, dpi_of, cursor, physical}` serve the tools and the spike, `window_dpi` sizes the tray icon, and `contains` says whether a box holds a point. |
| `WinLook` (`sysui`, `watch`) | `kx_platform::ui::SystemLook` | Dark apps (`AppsUseLightTheme`), the accent pair (`UISettings` `AccentDark1` and `AccentLight2`), the seven system colours while high contrast is on, animations off, the pointer size (`CursorBaseSize`, 32 when missing or outside Settings' 32 to 256), and the display language as a BCP-47 tag (empty when Windows cannot say). The first reading keeps the process-wide COM apartment alive for good (`CoIncrementMTAUsage`), so the cached `UISettings` factory outlives any thread that made it, such as Qt's GUI thread; no thread changes its COM mode. `watch` runs a hidden top-level window on its own thread, which hears Windows' change broadcasts and calls back there once per real change; dropping the guard ends the thread. |
| `scroll` | none | The scroll pad's pure rules (ADR-0029), for the scroll target the OS part builds on. `Wheel::per_line` turns a line into wheel delta from the user's wheel settings (`SPI_GETWHEELSCROLLLINES`, or `SPI_GETWHEELSCROLLCHARS` sideways), and none for 0 or a page (`PAGE_SCROLL`). A `Course` holds one run's state: each tick gives one `Turn`, sent while the pointer is on the target, else posted, else UI Automation's line steps; the part of a step left over carries to the next tick and resets when the target or way changes, and a turn stops at `MAX_TURN`. The caller turns only a step it will really send. A percent still for `check_ms` short of the end, while a whole notch of wheel delta went out, trips that target to UI Automation's steps until the target changes, and still under those steps it reads as the end; `next_route` says where the next turn goes. Only steps sent before the previous read count, so a target that shows them late is never judged early, and a read more than twice `check_ms` plus `read_ms` after the last starts the wait afresh. `along`, `reach` and `percent_moved` read UI Automation's percents, refuse bad ones and take a rounding within `END_SLACK` as the end, and `kx-gates` shares them; `lparam_point` reads a message's point back, and `area` refuses a box that is empty or further than the virtual screen's own size beyond it. |
| `scroll::entry` | none | The point before the keyboard: `from_history` and `to_history` map `GetMouseMovePointsEx`'s 16-bit display points, so a screen left of or above the main one stays negative. `last_outside` takes the newest history point outside the keyboard and on a screen's work area (the `Screens` port's `work_areas`), passing over the taskbar and the dead zones between screens. `pushed_out` puts a missed entry point `edge_px` past an edge of the keyboard, nearest edge first, and takes the first push that lands on a work area; when none does it gives none, and the user is asked to point at what to scroll. `target` takes the first, else the second, in physical pixels; none of them panics at the ends of the pixel range. `Kept` is what the guard keeps at an entry; the run checks its point against the screens of the moment, and its debug output hides every point. |
| `WinScroll` (`scroll::{run, ping, win, uia}`) | `kx_module_api::ports::ScrollTarget` | Each run aims at the window under the pointer, or, with the pointer on the keyboard, at the point kept before it entered; a point on our other windows aims at ours and turns nothing. A turn goes as a `SendInput` wheel tagged `TAG` while the pointer is still on the target and Windows routes wheels to the pointer (`SPI_GETMOUSEWHEELROUTING`), else as a posted `WM_MOUSEWHEEL` or `WM_MOUSEHWHEEL` whose point is in the target's own pixels (`PhysicalToLogicalPointForPerMonitorDPI`), else as UI Automation's line steps; a step UI Automation does not take is `Refused`, and a closed window is `Gone`. Each aim, turn and reach pings the target with `WM_NULL` (`SendMessageTimeoutW`, `read_ms`) from a thread of the run's own, one ping out at a time, and a ping Windows blocks (UIPI) counts as answered; a window that left one unanswered, owes one past `check_ms`, or that Windows calls hung (`IsHungAppWindow`) gets no turn and no read until it answers. `Pings` holds those ping rules, pure and tested everywhere. UI Automation runs on a COM thread of the run's own, started without waiting, with its timeouts at `read_ms`: it walks up to the first element with `ScrollPattern` for the box and percents, each read waits `read_ms` at most, a read waits behind one job at most and steps go only to a free thread. The wheel settings are read at the start and for each new target, and each check reads the clock once. |
| `WinBackdrop` (`backdrop`) | `kx_platform::ui::Backdrop` | Mica or Acrylic through DWM with the dark tint; `None` clears them. A Windows without system backdrops (before Windows 11 22H2) refuses a material with `Refused` before any other change, and the UI draws a solid plate. |
| `WinTray` (`tray`) | `kx_platform::ui::Tray` | The icon in the taskbar's notification area through `Shell_NotifyIconW` (version 4), one hidden top-level window and thread per icon. A click, Enter or Space, or the menu key on the icon calls back with where the menu opens; a front-window hook (our own process skipped) calls back "elsewhere" when a window outside the taskbar comes to the front. The icon's thread adds, changes and deletes the icon from its own queue, never holding a lock during a taskbar call, so the caller never waits on the taskbar; `TaskbarCreated` adds it again after Explorer restarts, and a taskbar not there yet gets it when it starts. The picture becomes a 32-bit icon with its alpha, sized for the DPI of the screen holding the taskbar (`screen::window_dpi`). Reading the callbacks, the tooltip and the picture's bytes is pure and tested everywhere; the calls are tested over a fake taskbar. |
| `WinPointerHook` (`hook`) | `kx_module_api::ports::PointerHook` | Runs a module's engine inside `WH_MOUSE_LL` and `WH_KEYBOARD_LL` on a thread of its own, one run per process (ADR-0027). The engine hears only the hand's mouse input, or with the simulated source only the gate tool's `SIM_TAG` input; our own `TAG` and `REPLAY` input passes as an echo, and wheels and side buttons pass untouched. The keyboard hook passes every key on: the engine hears an Esc press (the hand's, or our keyboard's `TAG`), and the hand's key-ups update the record of held input. After each callback the engine's input goes out in one `SendInput` batch tagged `REPLAY`, and the hand's input it lets through waits behind ours, so nothing overtakes it. Windows runs our hooks inside our own `SendInput`, so echoes heard then are noted right after the send, and the user's events heard then pass without the engine and are counted (`passed_inside`). A health check puts the hooks back after two checks in a row saw them miss input Windows saw, letting go first; the host keeps a fixed record of what our input holds down, and of a hand's press whose release the engine dropped, and lets go of it when the engine ends or the run stops. Dropping the run waits for that, `STOP_WAIT` at most, and `stats` gives numbers only, never a point or a key. |
| `release_now` (`hook`) | none | For the app's panic hook: asks a live hook thread to let go of everything our input holds, keeping its hooks and its run, and waits `RELEASE_WAIT` at most. It never panics, and returns at once with no live hook or on the hook thread itself. |
| `WinSpeaker` (`sound`) | `kx_platform::ui::Speaker` | Plays the compiled-in clips through `XAudio2` 2.9, loaded from System32 at the first play, on a thread of its own in COM's multithreaded apartment, so `play` only queues a message; a play past `QUEUE` is dropped, while the latest `prepare` always lands. It skips clips and clamps gains as the port says, and a `prepare` drops the engine, so the next play builds one for the new clips. Each clip gets `voices` source voices: a play takes an idle one, else replaces the one that started earliest. The engine stops after `idle_ms` of silence and starts again at the next play; a lost device or a failed start rebuilds it once per play, and each failure kind warns once until a play succeeds. Dropping it destroys the voices, then the mastering voice, then the engine, waiting `STOP_WAIT` at most. |
| `WinMemory` (`memory`) | `kx_platform::ui::Memory` | Gives the heaps' free pages back to Windows after a look change (`HeapOptimizeResources`, ADR-0023). |
| `WinInstance` (`instance`) | `kx_platform::ui::Instance` | One running copy per user session: a mutex in the session namespace (`Local\`). The claim's `listen` opens a message-only command window on its own thread, where the listener runs outside any lock; a later `listen` replaces the listener, even from inside it. Dropping the claim, like dropping a look watch, waits for a running listener. `send` posts `show` or `quit` as a code from one table; any other code is ignored. The command and watch windows ignore `WM_CLOSE` and a `WM_QUIT` posted to them or to their thread; only `stop` ends them (it sets a flag before its `WM_QUIT`), so no other program can close them. `instance::{parse, name}` read the command names. |

## Capabilities and settings

The adapter holds no capability of its own: the kernel grants capabilities to the modules that use its ports, the injector's and layout source's service keys need `InjectInput`, and `PointerHookKey` needs `PointerHook`. It has no settings. The hook's timings come in `HookConfig` from the mouse module's settings and the speaker's voices and idle time in `SpeakerConfig` from the `ui` module; the app folder name is `kx_platform::APP_DIR_NAME`, which also names the running copy's mutex and command window, and the apps that get key presses are the keyboard module's `key_apps` setting. The UI ports are the app's and the `ui` module's, not the kernel's, so they have no service key.

## Features

`sim-input` adds `WindowsPlatform::sim_pointer_hook`, whose engine acts only on the gate tool's `SIM_TAG` input. Only the app's `gate-input` test build turns it on, and `cargo xtask stage` refuses that build (ADR-0027).

## Security

See `docs/security/kx-platform-windows.md`. Every `unsafe` block has a scoped `#[allow(unsafe_code, reason = "...")]` and a `// SAFETY:` comment. The injector and the layout source never log; the injector's errors carry counts, never text, and a switch error names no layout. The window, look and tray parts never log either; a panic in a look, command or tray callback is caught before it reaches Windows. The pointer hook and the speaker log only counts, error codes and waits, never a point, a key or a sample. The scroll target and the entry watch never log a point or a box.
